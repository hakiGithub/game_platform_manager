# ADR-0029: 部署扩展步骤（部署期自动化）与 dnf-tw 指定版本部署

- 状态：Accepted
- 日期：2026-09-20
- 决策者：User（grill-with-docs 会话）
- 关联：[ADR-0002](0002-main-app-plugin-scope-isolation.md)（范围隔离）、[ADR-0006](0006-patch-install-decision-tree.md)（PatchInstallService）、[ADR-0008](0008-plugin-deploy-config-extension.md)（插件部署配置扩展）、[ADR-0009](0009-platform-capability-requirements.md)（dnf-tw 多实例依赖）、[ADR-0026](0026-host-tooling-container.md)（工具容器宿主能力）

## Context（背景）

**诉求**：部署流程目前没有"部署期自动化"能力——部署完成即终态。以 dnf-tw 为例，想部署默认版本之外的版本，必须在部署完成后手工改掉版本文件再重启，部署日志也看不到这类变更。目标是：在部署向导里选择目标版本（如 dnf-tw 指定版本部署），部署流程自动完成"补丁替换 + 脚本执行"，过程完整展示在部署日志里，实例第一次启动就是目标版本；补丁内容由该游戏的插件提供。

**现状事实**（2026-09-20 代码核对）：

1. `GameEnhancementExtension` 只有 `onInstanceCreate/Update/Start/Stop/Delete` 生命周期钩子（fire-and-forget、异常被吞掉），没有"部署完成"钩子；部署流程内的自动启动也不触发 `onInstanceStart`（`PluginLifecycleHook` 只在显式启停路径调用）。
2. 产品部署流程不经过任务中心：`DeployTaskHandler` 已注册 `(MAIN, deploy)` 但产品流程无人调用它；`InstanceServiceImpl` 直接 `deployService.deployAsync(…)`。部署日志只存内存（`DeployService.taskStatusMap`），由 `DeployProgress.vue` 轮询展示，服务重启即丢、无落库。
3. 补丁安装底座已存在：`PatchInstallService`（ADR-0006）提供 URL → 实例目标路径的完整链路（解压、sha256 校验、备份与自动回滚、宿主机/容器路由），plugin-l4d2 已在用。
4. dnf-tw 没有任何部署期版本选择：`dnf_tw.yml` 的 compose 模板把镜像 tag 写死（`llnut/dnf:debian13-qf1031-latest`），向导传入的 `gameVersion` 后端不消费；`variables` 是唯一的用户可填项。
5. dnf-tw 目前没有插件模块（backend 只有 plugin-l4d2）；ADR-0008 的"插件声明部署配置、主应用读时合并"机制已在 core 实现，但尚无插件使用。
6. 插件现有脚本手段：`FileAccessService.executeCommand(hostId, …)`（宿主机 SSH）与 `InstanceQueryService.executeCommand(instanceId, …)`（适配器路由）；没有 RUN_SCRIPT 类任务，脚本执行不进部署流程。

## Decision（决策）

### 决策 1：通用"部署扩展步骤"框架，dnf-tw 为第一个用例

主应用新增通用的部署扩展步骤能力：任何游戏插件都可声明"部署期扩展步骤"；dnf-tw 指定版本部署是首个用例，不做 dnf-tw 专用流程。游戏专属逻辑（版本目录、补丁、脚本）不写进主应用（ADR-0002 / ADR-0008 边界）。

### 决策 2：声明式步骤清单，由主应用部署管线执行

扩展步骤由插件声明（补丁来源 + 目标路径 / 脚本内容或来源 / 执行位置），主应用部署管线按清单顺序**阻塞式**执行，纳入部署日志与失败语义。不新增 `onInstanceDeployed` 式自由执行钩子。声明接口允许按实例配置动态计算步骤集（如按选中版本返回不同步骤集）。

### 决策 3：执行时点 = 部署动作完成后、实例正式启动与健康检查前

部署阶段（文件/容器就位）完成后进入扩展阶段：平台确保实例未运行 → 补丁替换 → 脚本执行 → 再进入既有健康检查与启动流程。对"部署即起容器"的适配器（docker-compose），扩展阶段先停实例、执行步骤、再走启动。目标是首次启动即目标版本，消除"先起错版本再重启"的中间态。

### 决策 4：重跑语义 = 每次部署都执行

扩展步骤不是"仅首次"：每次部署/重部署都执行。用户的版本选择随实例配置落库（configInfo），重部署按同一配方重放；步骤须按幂等设计。

### 决策 5：失败语义 = 步骤级致命性，默认致命

默认任一步骤失败 → 部署失败（实例 ERROR、不交付），补丁步骤沿用 `PatchInstallService` 自带备份回滚。步骤可声明非致命（可选优化类脚本），失败仅记日志。不采用"默认非致命"：用户选了指定版本、补丁没打上却交付一个能跑的错版本，是最糟的静默失败。

### 决策 6：补丁步骤复用 PatchInstallService，本期只做远端 URL 来源

补丁步骤声明 = URL（+可选 sha256）+ 目标相对路径（+可选 includePattern），走 `PatchInstallService` 全链路（解压、备份回滚、宿主机/容器路由）。插件 JAR 内置资源作为补丁来源（平台代传）留作后续增量，不在本期。

### 决策 7：脚本步骤标准执行位置 = 宿主机（SSH），容器内为步骤级可选

脚本可内嵌声明或 URL + sha256 拉取；标准执行在宿主机（SSH），输出进部署日志。步骤级可声明容器内执行（docker exec / compose exec），用于必须操作容器内进程或数据库的场景。依据：ADR-0006 决策 4"容器场景由宿主机代劳"是默认，但版本替换常需要容器内动作，故保留步骤级出口。

### 决策 8：扩展作为显式阶段进现有部署日志流；部署日志落库本期不做

部署日志（`DeployService.taskStatusMap` + `DeployProgress.vue` 轮询）新增显式阶段（如"扩展 / 版本定制"），每步开始/成功/失败/耗时以日志行呈现。部署日志与扩展结果落库不做（用户裁决，控制本期范围）——"服务重启即丢"属已知限制。

### 决策 9：dnf-tw 版本模型 = 镜像提供默认版本，其余版本由补丁 + 脚本产出

版本目录条目 = `版号 → 镜像 tag（可选，缺省沿用默认）+ 补丁集 + 脚本集 + 目标路径`。dnf-tw 现状：基础镜像只提供默认版本（qf1031），其他版本由插件提供的补丁包 + 脚本"改"出来；版本目录放插件声明（ADR-0008 读时合并体系）。dnf-tw 尚无可承载声明的插件模块——"是否随本次交付创建最小 plugin-dnf-tw"属实现范围问题，见 Consequences。

> **注（2026-09-24，实现回写 · 只做加法：本文决策 1–9 的正文一字未改）**：本注适用于本文把版本目录挂在「ADR-0008 读时合并 / 声明式合并体系」上的那两处表述——**决策 9 末句**与 **Consequences「版本目录的承载方」行**。实现落定的承载入口是**同一扩展点 `GameEnhancementExtension` 的类型化入口 `getDeployVersions`**，不是 `getDeployConfigs()`：ADR-0008 的读时合并**只作用于配置读取路径**（`GameServiceImpl` 给部署向导返回 `DeployConfigVO` 时整节替换、插件优先），**不作用于部署执行路径**（`InstanceServiceImpl.buildDeployConfig` 取的是 `game_metadata` 表里由扫描器落库的 yml 快照，不经那条合并视图）。⇒ 按字面把目录挂进 `getDeployConfigs()` 会做出一个「向导看得见、部署看不见」的目录，BR-12 / AC-20 / AC-24 同时落空。**本决策的边界不变**：版本目录仍由插件声明、仍在 ADR-0008 的声明体系之内，变的只是该体系里被选用的方法——这正是决策 1「游戏专属逻辑不写进主应用（ADR-0002 / ADR-0008 边界）」要保住的同一件事。依据：`docs/design/MERC-3/design.md` §16.1（那条不对称本身）与 §16.5（对 FR-22 措辞的偏离与回写建议）；事实登记：`docs/prd/MERC-3/prd.md` F-19 与 FR-22。

## Consequences（后果）

- 部署流程新增扩展阶段（DEPLOY 与 HEALTH_CHECK 之间），部署日志新增可见步骤；部署耗时增加"停实例 → 扩展 → 再启动"的固定成本。
- 失败语义收紧：默认致命 —— 选中指定版本但补丁失败时得到失败态，而不是静默的错版本；可选步骤用非致命声明保留弹性。
- 未声明扩展步骤的游戏/插件行为完全不变（向后兼容）；无插件时主应用基线流程不变。
- 版本目录的承载方：推荐随本次交付建最小 plugin-dnf-tw（版本目录 + 补丁/脚本声明）；过渡方案是版本目录先放 `dnf_tw.yml` 基线。两者都落在 ADR-0008 的声明式合并体系内，由 PRD / G0 确认。
- 部署日志仍为内存态：进程重启后历史日志丢失，无法作为长期审计证据（本期已知限制，Q8 裁决不做落库）。

## Alternatives（备选方案）

- **dnf-tw 专用流程写进主应用**：否 —— 与 ADR-0002 / ADR-0008"插件声明、主应用执行"边界相悖；换版本需求注定不止 dnf-tw 一家。
- **新增 `onInstanceDeployed` 钩子，插件自行执行**：否 —— 现有钩子是 fire-and-forget、异常被吞，日志进不了部署流、顺序与失败不可控；"展示到部署日志 + 失败可感知"两条硬需求只有主应用执行侧能保证。
- **扩展放在启动与健康检查全部通过之后**：否 —— 会引入"先起错版本再重启"的中间态，正是本需求要消除的。
- **仅首次部署执行一次扩展**：否 —— "首次"引入隐藏状态（重部署、换镜像、恢复备份都绕不开）；实例期望版本应由配置表达，重部署 = 重新达到目标状态。
- **参数化镜像 tag 作为版本机制（Q9-a）**：不适用于 dnf-tw —— 上游镜像只提供默认版本，其余版本没有现成镜像，必须靠补丁 + 脚本产出（用户裁决）。框架的版本目录仍保留"镜像 tag"可选字段。
- **部署日志与扩展结果落库**：本期不做（用户裁决），执行证据链本期末改变。
- **扩展做成任务中心任务、部署日志只留链接**：否 —— 与"展示到部署日志"直接冲突；且部署主流程本就不在任务中心。
