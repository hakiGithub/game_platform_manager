# L4D2 服务器管理面板 - 功能交互说明

## 文档说明

本文档详细描述 L4D2 服务器管理面板的前端与后端功能交互，包括页面功能、API 接口、数据流向、交互流程和技术实现要点。

---

## 1. 首页（仪表盘）

### 1.1 服务器状态卡片

**前端功能：**
- 显示当前地图名称
- 显示游戏模式（中文）
- 显示难度等级
- 显示在线人数（当前/最大）
- 显示服务器名称

**后端接口：**
```
POST /rcon/getstatus
响应: {
    "hostname": "服务器名称",
    "map": "当前地图",
    "players": "3/18",
    "difficulty": "专家",
    "gameMode": "合作",
    "users": [...]
}
```

**交互流程：**
```
页面加载
    ↓
定时器启动（每 5 秒）
    ↓
循环调用 POST /rcon/getstatus
    ↓
更新状态卡片数据
```

**技术实现要点：**
```
后端实现：
1. 使用 RCON 库建立到游戏服务器的 TCP 连接
2. 发送 "status" 命令获取服务器状态文本
3. 使用正则表达式解析文本提取关键信息
4. 发送 "z_difficulty" 获取难度
5. 发送 "sm_cvar mp_gamemode" 获取游戏模式
6. 将英文模式/难度转换为中文
7. 返回结构化 JSON 数据

关键正则：
- 玩家信息：#\s*(\d+)\s+(\d+)\s+"([^"]+)"\s+([A-Z_:0-9]+)\s+(\d+(?::\d+)+)\s+(\d+)\s+(\d+)\s+(\w+)\s+(\d+)\s+([0-9.]+:\d+)
- 难度提取："z_difficulty"\s*=\s*"([^"]+)"
- 模式提取："mp_gamemode"\s*=\s*"([^"]+)"
```

### 1.2 玩家列表

**前端功能：**
- 表格展示在线玩家
- 列：ID、昵称、SteamID、IP、地理位置、延迟、丢包率、连接时长
- 操作按钮：踢出、封禁
- 玩家数量统计

**数据来源：**
- 与状态卡片共用 `/rcon/getstatus` 接口
- `users` 数组包含玩家详细信息

**交互操作：**

| 操作 | 前端行为 | 后端接口 |
|------|---------|---------|
| 踢出玩家 | 确认弹窗 → 发送请求 | POST /rcon/kickuser |
| 封禁玩家 | 确认弹窗 → 选择是否踢出 → 发送请求 | POST /rcon/banuser |

**技术实现要点：**
```
IP 地理位置查询：
1. 使用 ip2region 数据库（xdb 格式）
2. 支持 IPv4 和 IPv6 查询
3. 查询结果缓存（LRU 缓存，避免重复查询）
4. 返回格式：国家|区域|省份|城市|ISP

玩家信息解析：
- 从 status 命令输出中解析每行玩家数据
- 提取：userid、name、uniqueid(SteamID)、duration、ping、loss、state、ip
- IP 格式：xxx.xxx.xxx.xxx:port，需去除端口部分再查询地理位置
```

### 1.3 快捷操作区

**前端功能：**
- 快速切换地图下拉框
- 修改难度按钮
- 修改游戏模式按钮
- 重启服务器按钮

**后端接口：**
```
获取地图列表：POST /rcon/maplist
切换地图：POST /rcon/changemap (mapName)
修改难度：POST /rcon/changedifficulty (difficulty)
修改模式：POST /rcon/changegamemode (gameMode)
重启服务器：POST /restart
```

## 2. 地图管理页面

### 2.1 地图列表

**前端功能：**
- 表格展示已安装地图
- 列：地图名称、文件大小、操作按钮
- 搜索/筛选功能
- 分页（如地图数量过多）

**后端接口：**
```
POST /list
响应: 文本格式，每行 "地图名$$文件大小"
```

**数据转换：**
```javascript
// 前端处理
response.split('\n')
  .filter(line => line.trim())
  .map(line => {
    const [name, size] = line.split('$$');
    return { name, size };
  });
```

**技术实现要点：**
```
后端实现：
1. 扫描 left4dead2/addons/ 目录
2. 筛选 .vpk 文件（地图文件格式）
3. 获取每个文件的尺寸（字节）
4. 转换为可读格式（KB/MB/GB）
5. 按文件名排序返回

文件路径：
- 游戏目录：${L4D2_GAME_PATH}/left4dead2/
- 地图目录：${L4D2_GAME_PATH}/left4dead2/addons/
- 地图列表文件：${L4D2_GAME_PATH}/left4dead2/maplist.txt
```

### 2.2 地图上传

**前端功能：**
- 拖拽上传区域
- 文件类型提示（.vpk, .zip, .rar, .7z）
- 上传进度条
- 上传结果提示

**后端接口：**
```
POST /upload
Content-Type: multipart/form-data
参数: map (文件)
响应: 200 上传成功 / 400 文件类型错误 / 500 服务器错误
```

**交互流程：**
```
用户选择/拖拽文件
    ↓
前端验证文件类型（正则匹配扩展名）
    ↓
使用 XMLHttpRequest 上传（支持进度）
    ↓
后端接收文件
    ↓
├─ .vpk：直接保存到 addons 目录
├─ .zip：解压后移动 vpk 文件
├─ .rar：调用 unrar 命令解压
└─ .7z：调用 7z 命令解压
    ↓
返回处理结果
```

**技术实现要点：**
```
文件处理逻辑：
1. 验证文件扩展名：\.(vpk|zip|rar|7z)$
2. 限制文件大小：最大 2GB
3. 检查磁盘空间：使用率超过 90% 拒绝上传
4. 清理文件名：去除特殊字符，保留字母数字下划线

压缩包处理：
- ZIP：使用标准库 archive/zip 解压
- RAR：调用系统命令 unrar x -o+ 解压
- 7Z：调用系统命令 7z x 解压
- 解压后递归查找 .vpk 文件，移动到 addons 目录

临时文件清理：
- 上传的临时文件在处理完成后删除
- 解压产生的中间文件及时清理
- 使用 defer 确保异常时也能清理
```

### 2.3 地图切换

**前端功能：**
- 地图选择弹窗
- 搜索过滤
- 官方地图/第三方地图分类

**后端接口：**
```
POST /rcon/changemap
参数: mapName
响应: 200 切换成功
```

**技术实现要点：**
```
RCON 命令执行：
1. 建立 TCP 连接到游戏服务器 RCON 端口
2. 发送认证包（RCON 密码）
3. 等待认证成功响应
4. 发送命令：changelevel <map_name>
5. 接收命令响应
6. 关闭连接

官方地图列表（硬编码）：
- 战役模式：c1m1_hotel, c1m2_streets, ...
- 生存模式：l4d_sv_lighthouse, ...
- 对抗模式：支持所有战役地图

地图代码转中文名：
- 调用外部 API：http://l4d2-maps.laoyutang.cn/{map_code}
- 缓存映射关系到本地，减少 API 调用
```

### 2.4 地图删除

**前端功能：**
- 删除确认弹窗
- 批量删除（可选）

**后端接口：**
```
POST /remove
参数: map (地图文件名)
响应: 200 删除成功
```

**技术实现要点：**
```
删除逻辑：
1. 验证文件名合法性（防止目录遍历攻击）
2. 检查文件是否存在于 addons 目录
3. 从 maplist.txt 中移除对应条目
4. 删除物理文件
5. 返回操作结果

安全措施：
- 只允许删除 .vpk 文件
- 路径拼接前验证文件名不含 ../ 等特殊序列
- 删除前确认文件位于允许的目录内
```

### 2.5 地图下载任务

**前端功能：**
- URL 输入框
- 添加下载任务按钮
- 下载任务列表（状态、进度）
- 取消/重试操作

**后端接口：**
```
添加任务：POST /download/add (url)
获取列表：POST /download/list
取消任务：POST /download/cancel (index)
重试任务：POST /download/restart (index)
清空列表：POST /download/clear
```

**技术实现要点：**
```
下载任务管理：
1. 使用内存中的任务队列（或数据库存储）
2. 每个任务包含：URL、文件名、状态、进度、错误信息
3. 后台 goroutine/线程池执行下载
4. 支持断点续传（HTTP Range 请求）

下载流程：
1. 解析 URL，提取文件名
2. 检查磁盘空间
3. 发送 HTTP HEAD 获取文件大小
4. 创建临时文件 .part
5. 分块下载，定期更新进度
6. 下载完成后移动到 addons 目录
7. 如果是压缩包，自动解压

并发控制：
- 限制同时下载数量（如 3 个）
- 每个下载使用独立的 goroutine/线程
- 使用 channel/队列进行任务调度
```

## 3. 插件管理页面

### 3.1 插件列表

**前端功能：**
- 卡片/表格展示插件
- 显示插件名称、状态（启用/禁用）、描述
- 启用/禁用开关
- 批量操作按钮

**后端接口：**
```
POST /plugins/list
响应: [
  {
    "name": "插件名称",
    "status": "enabled" | "disabled",
    "description": "插件描述"
  }
]
```

**技术实现要点：**
```
插件存储结构：
plugins/
├── 插件A/
│   └── left4dead2/
│       ├── addons/
│       │   └── sourcemod/
│       │       ├── plugins/
│       │       │   └── xxx.smx
│       │       └── configs/
│       │           └── xxx.cfg
│       └── cfg/
└── 插件B/
    └── ...

配置存储：
- 使用 YAML 文件记录启用状态
- 路径：plugins/plugins.yaml
- 格式：
  enabled_plugins:
    - name: 插件A
      files:
        - addons/sourcemod/plugins/xxx.smx
        - addons/sourcemod/configs/xxx.cfg

扫描逻辑：
1. 读取 plugins/ 目录下的所有子目录
2. 检查每个目录是否包含 left4dead2/ 子目录
3. 读取 plugins.yaml 获取启用状态
4. 合并数据返回列表
```

### 3.2 插件启用/禁用

**前端功能：**
- 单个插件开关
- 批量启用/禁用按钮
- 操作确认提示

**后端接口：**
```
启用单个：POST /plugins/enable (name)
禁用单个：POST /plugins/disable (name)
批量启用：POST /plugins/enable-batch (names: [])
批量禁用：POST /plugins/disable-batch (names: [])
```

**技术实现要点：**
```
启用插件流程：
1. 检查插件目录是否存在且结构正确
2. 检查是否已启用（避免重复）
3. 遍历插件目录下的所有文件
4. 使用 goroutine 池并发复制文件到游戏目录
5. 记录每个复制的文件路径到配置文件
6. 保存 plugins.yaml

禁用插件流程：
1. 从 plugins.yaml 中查找插件记录
2. 遍历记录的文件列表
3. 删除游戏目录中对应的文件
4. 从 plugins.yaml 中移除该插件记录
5. 保存配置文件

并发复制实现：
- 使用线程池（Go: ants 库 / Java: ExecutorService）
- 池大小：CPU 核心数
- 每个文件一个任务
- 使用 WaitGroup 等待所有任务完成
- 使用互斥锁保护配置文件写入

错误处理：
- 复制失败时回滚已复制的文件
- 记录错误日志
- 返回详细的错误信息
```

### 3.3 插件上传

**前端功能：**
- 文件选择（.zip）
- 上传进度显示
- 自动识别插件结构

**后端接口：**
```
POST /plugins/upload
Content-Type: multipart/form-data
参数: file
响应: 200 上传成功
```

**插件包结构要求：**
```
插件包.zip
└── left4dead2/
    ├── addons/
    └── cfg/
```

**技术实现要点：**
```
上传处理逻辑：
1. 验证文件类型（仅 .zip）
2. 打开 ZIP 文件，列出所有条目
3. 处理文件名编码（GBK 转 UTF-8）
4. 验证目录结构：
   - 单插件：所有文件在 left4dead2/ 下
   - 多插件：每个插件一个目录，包含 left4dead2/
5. 检查目标目录是否已存在
6. 解压文件到 plugins/插件名/
7. 清理临时文件

编码处理：
- ZIP 文件可能使用 GBK 编码（中文 Windows 环境）
- 尝试 UTF-8 解码，失败则使用 GBK 解码
- 使用 transform 库进行编码转换

安全检查：
- 防止 Zip Slip 攻击（验证解压路径）
- 跳过 __MACOSX/ 和 .DS_Store 等系统文件
- 限制单个文件大小
```

**前端功能：**

- 预设详情查看

**后端接口：**
```
获取预设：POST /plugins/presets
响应: [{
  "name": "预设名称",
  "description": "描述",
  "plugins": ["插件A", "插件B"]
}]

```

**技术实现要点：**
```
预设存储：

    - name: 基础预设

4. 先禁用不需要的插件
5. 再启用需要的插件
6. 返回操作结果（成功/失败的插件列表）

原子性考虑：
- 如果中间步骤失败，已完成的操作不回滚
- 记录详细的操作日志
- 返回部分成功的状态
```

## 4. 性能监控页面

### 4.1 实时监控面板

**前端功能：**
- CPU 使用率仪表盘
- 内存使用进度条
- 磁盘使用进度条
- 网络上传/下载速度
- 自动刷新（每秒）

**后端接口：**
```
POST /monitor/status
响应: {
  "cpu_percent": 45.2,
  "cpu_max_core": 78.5,
  "mem_total": 16777216000,
  "mem_used": 8388608000,
  "swap_total": 4294967296,
  "swap_used": 1073741824,
  "disk_total": 107374182400,
  "disk_used": 53687091200,
  "net_up_speed": 102400,
  "net_down_speed": 204800,
  "timestamp": 1699999999
}
```

**交互流程：**
```
进入监控页面
    ↓
启动定时器（每秒）
    ↓
循环调用 /monitor/status
    ↓
更新图表数据
```

**技术实现要点：**
```
系统监控实现：
1. 后台启动定时任务（每秒执行）
2. 采集各项系统指标
3. 存储到内存（供实时查询）
4. 可选：写入数据库（供历史查询）

CPU 监控：
- Go: gopsutil/cpu.Percent()
- Java: OSHI CentralProcessor
- 计算总使用率和每个核心的使用率
- 取最大核心使用率作为 cpu_max_core

内存监控：
- 获取物理内存总量、已用、可用
- 获取交换分区总量、已用
- 单位：字节

磁盘监控：
- 监控游戏目录所在分区的使用情况
- 获取总容量和已用容量

网络监控：
- 读取 /proc/net/dev（Linux）
- 或使用系统库获取网络接口统计
- 计算每秒上传/下载速度（当前值 - 上次值）
- 排除 docker/veth/lo 等虚拟接口

Docker 环境特殊处理：
- 挂载宿主机的 /proc 到容器 /host/proc
- 从 /host/proc/1/net/dev 读取网络统计
- 从 /host/proc/stat 读取 CPU 统计
```

### 4.2 历史数据图表

**前端功能：**
- 时间范围选择器（最近1小时/24小时/7天/自定义）
- 多指标折线图（CPU、内存、网络）
- 数据缩放/平移
- 导出数据（可选）

**后端接口：**
```
POST /monitor/history
参数: start（时间戳）, end（时间戳）
响应: [
  {
    "timestamp": 1699999900,
    "cpu_percent": 40.0,
    "mem_used": 8.5,
    "net_up_speed": 100.0,
    "net_down_speed": 200.0
  }
]
```

**技术实现要点：**
```
数据存储：
- 使用 SQLite 数据库存储历史数据
- 表结构：system_metrics
  - id, timestamp, cpu_percent, cpu_max_core, 
  - mem_used, swap_used, net_up_speed, net_down_speed, disk_used
- 每秒写入一条记录

数据清理：
- 定期清理过期数据（如保留 30 天）
- 使用定时任务每天执行清理

降采样算法（LTTB - Largest Triangle Three Buckets）：
- 当数据量 > 2000 时进行降采样
- 目标点数：约 720 个（适合图表展示）
- 算法步骤：
  1. 将数据分成 buckets 个区间
  2. 每个区间选择一个代表性点
  3. 使用三角形面积最大化原则选择点
  4. 保留极值点（最大/最小值）

SQL 降采样（简单方法）：
- 按时间分桶，取每个桶的最大值
- SELECT CAST(timestamp / ? AS INTEGER) * ? as bucket_time, MAX(cpu_percent) ...
- GROUP BY bucket_time

数据单位转换：
- 存储时统一使用基本单位
- 返回时转换为可读单位：
  - 内存/磁盘：GB
  - 网络：KB/s
  - CPU：百分比
```

```

2. 发送认证包：

   - 4字节：请求ID
   - 4字节：类型（3=SERVERDATA_AUTH）

   - 1字节：空字符

   - 类型（2=SERVERDATA_EXECCOMMAND）
   - 内容：命令字符串
5. 接收响应包（可能多个）
6. 关闭连接

包格式：
| 长度(4B) | 请求ID(4B) | 类型(4B) | 内容(NB) | 空(1B) |

- 每次命令新建连接（简单但开销大）
- 或使用连接池复用连接（性能更好）
- 注意：RCON 连接不是线程安全的

超时处理：
- 连接超时：5 秒
- 读取超时：10 秒
- 超时后关闭连接，返回错误
```
