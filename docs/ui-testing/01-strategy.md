# 01 - 测试策略与分层

> Game Platform Manager - UI 测试顶层策略

---

## 1. 测试目标

### 1.1 核心目标
1. **保证业务正确性**：用户能够完成核心业务流程（部署实例、管理插件、RCON 操作等）
2. **保证 UI 一致性**：菜单、布局、交互行为在不同模块间保持一致
3. **保证集成稳定性**：主应用与 Wujie 子应用通信可靠，路由切换无 404/403
4. **保证回归可控**：每次发版前通过自动化 + 手动清单快速回归

### 1.2 非目标
- 性能压测（由后端 JMeter 负责）
- 安全测试（由后端 SAST/DAST 负责）
- 视觉像素级回归（暂不要求）

---

## 2. 分层原则

采用**测试金字塔**模型，从下到上：

```
        /\
       /E2E\         少量，覆盖核心业务流（10%）
      /------\
     /Integration\   中量，覆盖跨模块协作（20%）
    /--------------\
   /   Component    \ 较多，覆盖独立组件行为（40%）
  /------------------\
 /     Unit           \大量，覆盖纯函数/工具/Store（30%）
/----------------------\
```

### 2.1 各层职责

| 层级 | 范围 | 工具 | 执行频率 |
|------|------|------|----------|
| Unit | utils、stores、纯函数 | Vitest + happy-dom | 每次 commit |
| Component | Vue 组件、Element Plus 交互 | Vue Test Utils + Vitest | 每次 commit |
| Integration | 跨组件、跨 Store、API Mock | Vitest + MSW | 每次 PR |
| E2E | 真实浏览器业务流 | Playwright（规划）/ TRAE browser_use | 发版前 |

### 2.2 命名约定

- 测试文件：`{被测文件名}.test.{ts|js}`
- describe 块：`被测单元名称`（如 `'useUserStore'`）
- it 块：`应该 + 期望行为`（如 `'应该正确登录并存储 token'`）

## 4. 测试数据策略

### 4.1 单元/组件测试
- 使用 Mock 数据，不依赖真实后端
- API 调用通过 `vi.mock` 或 MSW 拦截
- Store 测试使用独立 Pinia 实例

### 4.2 E2E 测试
- 使用真实后端（开发环境）
- 测试账号：`admin / admin123`
- 测试数据：每次运行前重置 SQLite 数据库或使用独立测试库

## 6. 风险与约束

1. **Wujie 微前端复杂性**：子应用加载、iframe 沙箱、样式隔离可能导致 E2E 难以直接操作子应用 DOM
2. **真实 SSH/Docker 依赖**：部分 E2E 场景需要真实主机和容器，难以在 CI 环境复现
3. **数据状态依赖**：测试用例之间可能存在数据依赖（如创建实例后才能测试启动）

### 缓解措施
- Wujie 子应用 E2E 使用 `browser_evaluate` 直接操作子应用 window
- 依赖真实后端的场景标记为 "manual"，仅在本机执行
- 提供 `scripts/reset-test-data.ps1` 重置测试数据（规划中）
