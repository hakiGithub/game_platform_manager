## 1. 一句话定义

在部署流程中新增由游戏插件声明、由主应用部署管线执行的**部署扩展步骤**（补丁替换 + 脚本执行），使用户可以在部署向导中选择目标版本（首个用例为 dnf-tw），实例**第一次启动即为所选版本**，全过程与失败结果在部署日志中可见可判。

---

## 2. 背景与问题

### 2.1 问题

部署流程今天是「部署即终态」：部署动作完成即交付，没有部署期自动化能力。以 dnf-tw 为例，上游镜像只提供默认版本，要部署其他版本必须在部署完成后**手工替换版本文件并重启**，且部署日志中看不到这类变更。带来的直接后果：

- 交付过程被割裂成「平台部署 + 人工改造」，人工步骤无记录、无校验、不可重放。
- 部署日志无法反映实例最终状态的形成过程，失败无法归因。

## 3. 目标与成功标准

### 3.1 目标（G-）

| 编号 | 目标 | 对应决策 |

| G-01 | 交付**通用**部署扩展步骤能力：任意游戏插件均可声明本游戏的部署扩展步骤，由主应用部署管线统一执行；主应用内不存在任何 dnf-tw 专用分支 | 决策 1 |

## 7. 功能需求（FR-）

### 7.2 声明模型

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| FR-05 | 主应用提供按 `gameCode` 归属的扩展声明接口；插件可为**具体实例的配置（含所选版本）动态计算步骤集**；主应用不解释游戏语义 | P0 | AC-06、AC-18 |
| FR-06 | 步骤类型两类：`PATCH`（补丁替换）与 `SCRIPT`（脚本执行）；步骤集为**有序**清单，序号自 1 起 | P0 | AC-06 |
| FR-07 | 补丁步骤声明字段：`url`（必填）、`targetPath`（必填，实例相对路径）、`sha256`（可选）、`includePattern`（可选）、`fatal`（可选，默认致命）——字段口径见 §8.2 | P0 | AC-08、AC-11 |
| FR-08 | 脚本步骤声明字段：`label`、内容二选一（内嵌脚本正文 / `url` + `sha256` 拉取）、`position`（`host` 默认 / `container` 可选）、`fatal`（默认致命）；执行输出进部署日志——字段口径见 §8.3 | P0 | AC-12、AC-13 |
| FR-09 | 版本目录条目模型：`版号 → 镜像 tag（可选，缺省沿用默认）+ 补丁集 + 脚本集 + 目标路径`；`镜像 tag` 字段为框架通用能力保留，dnf-tw 本期不使用（无现成镜像，ADR-0029 Q9-a） | P0 | AC-01、AC-14 |

### 7.3 执行管线

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| FR-10 | 部署流水线新增**部署扩展阶段**，位置 = `DEPLOY` 完成之后、`HEALTH_CHECK` 之前 | P0 | AC-04 |
| FR-11 | 进入扩展阶段前，平台须确保实例处于未运行状态；对「部署动作即起容器」的适配器（docker-compose / linuxgsm-docker），扩展阶段先停实例、执行步骤、再进入既有启动与健康检查 | P0 | AC-04、AC-05 |
| FR-12 | 步骤由主应用部署管线**阻塞、按声明顺序**执行：上一步判定完成前不进入下一步；同实例内不并发执行 | P0 | AC-06 |
| FR-13 | 每次部署都执行扩展步骤（含首次部署、retry-deploy、后续重部署），按实例配置中记录的同一份版本配方重放；不存在「仅首次」语义 | P0 | AC-07 |
| FR-14 | 补丁步骤复用 `PatchInstallService` 全链路（下载、解压、sha256 校验、备份与自动回滚、宿主机/容器路由），不得另起一套补丁落位实现 | P0 | AC-09、AC-11 |
| FR-15 | 脚本步骤在声明位置执行并回收 `stdout` / `stderr` / 退出码，输出进部署日志；`exitCode ≠ 0` 判为步骤失败 | P0 | AC-12、AC-13 |
| FR-16 | 扩展阶段未判定完成前，不得进入 `HEALTH_CHECK` 与 `START`，实例不得被置为可交付 | P0 | AC-05、AC-08 |

### 7.4 失败语义

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| FR-17 | 致命步骤（默认）失败 → 扩展阶段终止、不执行其后步骤、部署判为失败、实例 `ERROR`、不启动、不交付；日志须指明失败步骤标识与原因 | P0 | AC-08 |
| FR-18 | 非致命步骤失败 → 记 WARN 日志行（含步骤标识与原因）、继续后续步骤、部署照常完成 | P0 | AC-10 |
| FR-19 | 补丁步骤致命失败时沿用 `PatchInstallService` 自动回滚：目标路径恢复到本次改动前状态，且日志可见回滚结果 | P0 | AC-09 |

### 7.5 日志呈现

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| FR-20 | 扩展阶段作为显式阶段进入现有部署日志流：阶段可见 + 每步「开始 / 成功或失败 / 耗时」行；复用 `LogEntryVO{level,message,stage,time}` 结构，不新增前端拉取通道 | P0 | AC-03、AC-16 |
| FR-21 | 部署日志本期仍为内存态（`taskStatusMap`）；进程重启后历史丢失属已知限制，本期不落库 | P0 | AC-17 |

## 8. 字段与数据口径

### 8.1 版本目录（Version Catalog）条目

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `versionId` | string | 是 | — | 同一游戏内唯一；非空；仅 `[A-Za-z0-9._-]` | 版号，即用户在向导看到的值 |
| `displayName` | string | 否 | `versionId` | — | 展示名（文案归 @Designer） |
| `imageTag` | string | 否 | 缺省 ⇒ 沿用游戏 compose 模板既有 tag | — | 框架保留字段；dnf-tw 本期不用（F-09） |
| `patches[]` | list | 否 | 空 | — | 见 §8.2 |
| `scripts[]` | list | 否 | 空 | — | 见 §8.3 |
| `default` | boolean | 否 | false | 同一游戏至多一条为 true | 标记默认版本条目 |

**默认版本语义**（BR-02）：目录中不存在扩展步骤、或用户未做选择的版本 = 默认版本 = 不执行扩展步骤 + 沿用 `dnf_tw.yml` compose 模板内既有镜像 tag 字面量。

### 8.2 补丁步骤（PATCH）

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `label` | string | 否 | 序号 + `PATCH` | — | 日志展示名 |
| `url` | string | 是 | — | 合法 http(s) URL | 补丁包来源（本期仅远端 URL，决策 6） |
| `targetPath` | string | 是 | — | 见 BR-05 | 实例相对路径（宿主安装目录或容器工作目录相对） |
| `sha256` | string | 否 | 不校验 | 64 位十六进制 | 完整性校验 |
| `includePattern` | string | 否 | 全部落位 | 逗号分隔 glob | 仅压缩包生效 |
| `format` | string | 否 | 按扩展名判定 | 沿用 `PatchFormat` 取值 | 压缩包格式 |
| `fatal` | boolean | 否 | **true** | — | 步骤致命性 |

**本期硬约束**：`headers` 不作为可声明字段（F-07 现有链路不承载）。若需要带鉴权头的补丁来源，另立需求，不混入本期。

### 8.3 脚本步骤（SCRIPT）

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `label` | string | 是 | — | 非空 | 日志展示名 |
| `content` | string | 与 `url` 二选一 | — | 二者必须恰有一个 | 内嵌脚本正文 |
| `url` + `sha256` | string | 与 `content` 二选一 | `sha256` 缺省不校验 | 合法 http(s) URL | 远端脚本 |
| `position` | enum(`host`\|`container`) | 否 | **`host`**（SSH） | — | 决策 7 |
| `fatal` | boolean | 否 | **true** | — | 步骤致命性 |
| `timeoutMs` | integer | 否 | 待定（OP-04） | > 0 | 步骤超时 |

### 8.4 实例配置（`configInfo`）口径

| 键 | 写入方 | 含义 | 规则 |
| --- | --- | --- | --- |
| 版本专用键（推荐名 `deployVersion`，最终名归技术设计但必须满足 BR-07） | 部署向导提交 | 用户所选 `versionId` | 必须是**带前缀专用键**；不得与任一 `variables[].name` 同名（F-11 变量扁平铺顶部的既有事实） |
| `gameVersion` | 前端既有代码 | 恒为 `undefined` 的**坏键** | 不得复用承载本期语义（F-11、RISK-10） |
| `variables[].name` 各键 | 部署向导 | compose 变量值 | 语义不变，不与版本键互相覆盖 |

### 8.5 部署日志条目

沿用 `LogEntryVO{id,level,message,stage,time}` 与 `level ∈ INFO/WARN/ERROR/SUCCESS`。约束：扩展阶段的每条日志 `stage` 值一致且可与既有阶段区分；步骤失败行 `level = ERROR`（致命）或 `WARN`（非致命）。

## 9. 状态机（实例运行状态视角）

| 时机 | 阶段 | 期望 `run_status` |
| --- | --- | --- |
| 提交部署 | `INIT`～`PORT_CHECK` | `INSTALLING`(5) |
| 资源就位 | `PRE_DEPLOY`、`DEPLOY` | `INSTALLING` |
| **进入扩展阶段** | 扩展 | `INSTALLING`；且实例进程/容器处于停止（FR-11） |
| 致命步骤失败 | 扩展 | `ERROR`(4)，不进入 `START`（FR-17） |
| 非致命步骤失败 | 扩展 | 仍继续 → `HEALTH_CHECK` |
| 扩展判定完成 | `HEALTH_CHECK` → `UPDATE_STATUS` | 既有语义不变：`STOPPED`(0) |
| 启动并复检通过 | `START` → `COMPLETE` | `RUNNING`(1)，**首启即目标版本** |

## 10. 业务规则（BR-）

| 编号 | 规则 | 依据 |
| --- | --- | --- |
| BR-01 | 版本目录与扩展步骤的唯一承载方是**游戏插件声明**（ADR-0008 读时合并体系）；主应用 `core/` 不得内置任何游戏专属版本表或版本判断逻辑 | 决策 1、9；ADR-0002 |
| BR-02 | 「默认版本」= 不执行扩展步骤 + 沿用游戏 compose 模板既有镜像 tag；用户未做选择即等价默认版本，行为与现状一致 | 决策 9；F-09；AC-02 |
| BR-03 | 版本选择是实例部署配方的一部分：换版本走「改实例配置 → 重新部署」，不提供部署后就地改版本的旁路 | 决策 4；FR-13 |
| BR-04 | 步骤致命性默认 `true`；非致命只能由声明侧显式给出，主应用不得推断或覆盖 | 决策 5 |
| BR-05 | 补丁 `targetPath` 必须是相对实例安装目录 / 容器工作目录的安全相对路径；拒绝绝对路径与目录越界（`..`）；落位口径沿用 `PatchInstallService` | ADR-0006；F-05 |
| BR-06 | 步骤必须按幂等设计：在已达目标状态的实例上重复执行须成功且结果不变；幂等性由声明方（插件）负责，主应用不判断「是否已做过」 | 决策 4 |
| BR-07 | 版本键与 compose 变量键共存于同一扁平结构，因此版本键必须是独立专用键，且声明期与提交期都要校验与 `variables[].name` 不同名 | F-11 |
| BR-08 | 主应用按声明顺序执行，不重排、不同实例内并发；`PATCH` 与 `SCRIPT` 混排时同样遵循声明顺序 | 决策 2 |
| BR-09 | 补丁步骤沿用既有资源约束：全局并发 3、每宿主机互斥、自动重试 2 次（5s/20s 退避）、备份保留 5 份 | F-05 |
| BR-10 | 扩展阶段不改变既有阶段语义：`HEALTH_CHECK` / `START` 的判定标准、`UPDATE_STATUS` 置 `STOPPED`、`COMPLETE = 100%` 均不变 | 决策 8 |
| BR-11 | 未声明扩展步骤的游戏与插件，其部署阶段序列、进度百分比语义、状态转移与结果必须与改造前等价（回归基线） | 决策 2、8；G-04 |
| BR-12 | **（派生规则，待 G0 确认）** 当用户**显式选择了非默认版本**而该游戏的扩展声明不可用（插件未加载 / 声明接口异常 / 所选 `versionId` 不在目录中）时，部署必须失败并给出可辨识原因，**不得静默按默认版本交付**。依据：决策 5 对「选了指定版本却交付错版本是最糟的静默失败」的判定。此项在 Issue 正文与 ADR 中未逐字出现，见 OP-06 | 决策 5（推论） |
| BR-13 | 部署日志为内存态，本期不作为长期审计证据；验收证据须在部署过程内当次采集 | 决策 8；F-03 |

## 11. 空态 / 异常态 / 无权限态

| 场景 | 触发条件 | 系统表现 | 用户可见 |
| --- | --- | --- | --- |
| 无版本目录 | 游戏无插件 / 插件未加载 / 目录为空 | 向导不展示版本选择项；提交载荷无版本键 | 与现状无差异（AC-02） |
| 目录仅默认版本 | 只声明 `default = true` 条目 | 展示选择项但只有一个可选值 | 是否隐藏单值控件归 @Designer（OP-05） |
| 无扩展声明但有目录 | 目录条目 `patches`/`scripts` 均空 | 走默认版本路径，不进入扩展阶段 | 与现状无差异 |
| 声明不可用 + 显式非默认版本 | 插件异常 / 版本不在目录 | 部署失败，实例 `ERROR`，不启动 | 失败原因指名「版本声明不可用」 （BR-12，待确认） |
| 补丁下载失败 / sha256 不符 | URL 不可达、校验不通过 | 步骤失败 → 致命则部署失败；沿用补丁重试 | 日志含失败步骤与原因（AC-11） |
| 补丁目标回滚失败 | 备份不可用 | 部署失败，实例 `ERROR`，日志标注回滚结果 | 需人工介入（AC-09） |
| 脚本非零退出 | `exitCode ≠ 0` | 判失败，按致命性处理 | 日志含 exitCode 与输出（AC-12） |
| 脚本超时 | 超过 `timeoutMs` | 判失败，按致命性处理 | 阈值取值待 OP-04 |
| 容器内执行但容器未运行 | `position = container` 时容器不存在 | 步骤失败（扩展阶段实例应为停止，见 FR-11） | 日志含可辨识原因；该组合是否合法由技术设计定（RISK-05） |
| 宿主机 SSH 不可达 | 主机凭证失效 | 步骤失败 → 致命则部署失败 | 日志含主机与原因 |
| 未登录 / 凭证过期 | 调用部署或日志接口 | HTTP 401 / 403 | 沿用平台既有登录页跳转，无新增权限态（§4.2） |

## 12. 验收标准（AC-）

### 12.1 用例

| 编号 | 前置 | 操作 | 预期结果 |
| --- | --- | --- | --- |
| AC-01 | dnf-tw 插件声明了含 ≥2 条目的版本目录 | 打开部署向导，选 dnf-tw + docker-compose | 出现目标版本选择项，选项与目录 `versionId` 一致，默认项为默认版本；确认部署摘要显示所选版本（FR-01/04/09） |
| AC-02 | 同上 | 不做版本选择（保持默认）提交部署 | 无扩展阶段步骤行；阶段序列与现状一致；实例以默认版本运行；`configInfo` 除版本键外与现状一致（FR-02/BR-02） |
| AC-03 | 选择非默认版本 | 提交部署并轮询 `GET /api/instances/{id}/deploy-progress` | 日志出现扩展阶段；每个已执行步骤都有开始行、成功或失败行、耗时行，`stage` 可区分（FR-20/KPI-02） |
| AC-04 | 选择非默认版本（dnf-tw 为 docker-compose） | 完成部署 | 扩展阶段出现在 `DEPLOY` 之后、`HEALTH_CHECK` 之前；进入扩展阶段前实例处于停止状态（FR-10/FR-11） |
| AC-05 | 选择非默认版本且补丁生效 | 观察部署结束后的实例 | 实例进入 `RUNNING` 且**首次启动即目标版本**；全程无人工改文件、无人工重启；`HEALTH_CHECK`/`START` 判定标准未被绕过（FR-16/G-02） |
| AC-06 | 声明 2 个及以上步骤（PATCH 与 SCRIPT 混排） | 部署 | 步骤严格按声明序号串行执行；步骤 N 未判定完成前不出现步骤 N+1 开始行（FR-05/06/12/BR-08） |
| AC-07 | 实例已部署完成 | 改一次无关配置后重新部署（或走 retry-deploy） | 扩展阶段再次执行**同一**步骤集并重放成功；版本键读取自 `configInfo`（FR-13/BR-03） |
| AC-08 | 声明一个致命补丁步骤并使其失败（URL 不可达） | 部署 | 其后步骤不执行；部署判失败；实例 `ERROR`；未进入 `START`；日志指明失败步骤标识与原因（FR-17） |
| AC-09 | 同 AC-08，且目标路径在补丁前已有文件 | 部署 | 目标路径恢复到改动前状态（备份生效）；日志可见回滚结果；未交付错版本（FR-19） |
| AC-10 | 声明一个 `fatal = false` 脚本步骤并使其 `exitCode ≠ 0`，其余步骤致命且成功 | 部署 | 该步骤 `WARN` 行；后续步骤照常执行；部署 `COMPLETE`、实例可 `RUNNING`（FR-18） |
| AC-11 | 补丁步骤声明 `sha256` 且值与包实际摘要不符 | 部署 | 步骤判失败；致命性为 true 时部署失败（FR-07/14） |
| AC-12 | 脚本步骤 `position = host`（缺省）且输出可见内容 | 部署 | 经宿主机 SSH 执行；`stdout`/`stderr`/exitCode 进部署日志；`exitCode ≠ 0` 判失败（FR-08/15） |
| AC-13 | 脚本步骤 `position = container` | 部署 | 在目标容器内执行且输出进日志；不落到宿主机执行路径（FR-08/15） |
| AC-14 | 版本目录条目声明了非默认 `imageTag`（框架能力用例，可用第二个游戏或桩插件） | 部署 | 生成的 compose 使用所声明 tag；未声明时模板文本不变（FR-09） |
| AC-15 | 未声明扩展步骤的游戏（例：l4d2 或任一 linuxgsm 游戏） | 走完整部署 | 阶段序列、状态转移、进度百分比语义、日志结构、最终结果与改造前逐项目一致（G-04/BR-11） |
| AC-16 | 扩展阶段执行中 | 观察前端部署日志面板 | 用户可辨识当前处于扩展阶段及正在执行的步骤标签；无需新接口即达成（FR-20） |
| AC-17 | 部署完成后重启主应用进程 | 查询历史部署日志 | 历史丢失属预期；本期不新增落库验收；验收证据当次采集（FR-21/BR-13） |
| AC-18 | 同游戏两实例选择不同版本 | 分别部署 | 两者日志步骤集与所选版本一一对应，互不串用（动态步骤集能力，FR-05） |
| AC-19 | 完成一次非默认版本部署 | 读 `GET /api/instances/{id}` 的 `configInfo` 与库中 `config_info` | 版本专用键存在且等于所选 `versionId`；未覆盖任何同名 compose 变量键（FR-03/BR-07） |
| AC-20 | 关闭插件或让声明接口抛异常，且用户显式选了非默认版本 | 部署 | 部署失败且原因指名版本声明不可用；未静默按默认版本交付（**BR-12 生效后方可执行；BR-12 被否决则本条作废**） |

## 14. 风险（RISK-）

| 编号 | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| RISK-01 | 扩展阶段引入「停实例 → 补丁/脚本 → 再启动」的固定成本 | 部署总耗时上升，慢补丁来源会拉长反馈；进度条停滞观感 | 每步耗时可见（FR-20）；超时声明（§8.3）；耗时阈值上线后据实评估（KPI-02 先建测量能力） |
| RISK-02 | `headers`/`includePattern` 在任务 payload 序列化时丢失（F-07 有行号证据） | 决策 6 承诺的 `includePattern` 直接复用即失效；本期已排除 `headers` | 列入依赖，要求设计侧补齐字段透传或改用同链路内执行；AC-11 之外补测 includePattern 落位 |
| RISK-03 | `install()` 异步语义与扩展阶段「阻塞 + 过程进日志」冲突（F-06） | 若设计不解决，日志只有开始/结束两行，KPI-02 无法达标 | FR-12/FR-20 作为验收硬门；设计需给出进度桥接或同步通道 |
| RISK-04 | 部署日志内存态（F-03） | 进程重启即丢证据，失败难复现；审计不可用 | BR-13 明确限制；验收当次采集（AC-17）；落库另立需求（N-03） |
| RISK-05 | 「扩展前先停实例」对 compose 类适配器语义不清（stop 与 down 的数据/网络后果不同），且停失败无裁决 | 可能引发数据目录/卷状态或容器名冲突问题 | 交 @Architect 定义；PRD 只约束「停止状态」这一可观察结果（FR-11） |
| RISK-06 | OP-02 资料缺失 | 无法端到端验证补丁与脚本，AC-05/09/11/12/13 与 KPI-03 不可测 | 本期降级为「框架 + 版本目录占位模板」，并在验收记录标注不可测项（禁止编造资料） |
| RISK-07 | `configInfo` 变量与版本键同处扁平结构（F-11） | 键名撞车会导致变量值被静默覆盖 | BR-07 校验 + AC-19 断言 |
| RISK-08 | 脚本步骤扩大插件侧可执行的命令面（宿主机 root 用户或容器内任意 shell） | 越权、误删、不可审计 | 声明只出自插件代码（非运行时可配）；不新增用户输入面；要求设计保留命令文本日志（沿用 F-13 通道既有 INFO 记录） |
| RISK-09 | retry-deploy 既有路径先 `adapter.uninstall(...)` 再部署（F-04），与扩展阶段先后关系未覆盖 | 重部署可能落在已被卸载的状态上 | 交 @Architect 明确；FR-13 只约束「必须重放」 |
| RISK-10 | 前端 `gameVersion` 是恒 `undefined` 的坏键（F-11） | 复用它会造成「选了版本但什么都没存下」 | BR-07/§8.4 规定独立专用键；AC-19 断言落库 |
| RISK-11 | 无插件模块即无声明载体（F-08/F-14），框架交付后无可接入方 | G-01/G-02 端到端不成立 | 见 OP-01 推荐（随交付建最小插件） |
