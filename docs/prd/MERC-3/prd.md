## 1. 一句话定义

在部署流程中新增由游戏插件声明、由主应用部署管线执行的**部署扩展步骤**（补丁替换 + 脚本执行），使用户可以在部署向导中选择目标版本（首个用例为 dnf-tw），实例**第一次启动即为所选版本**，全过程与失败结果在部署日志中可见可判。

---

## 2. 背景与问题

### 2.1 问题

部署流程今天是「部署即终态」：部署动作完成即交付，没有部署期自动化能力。以 dnf-tw 为例，上游镜像只提供默认版本，要部署其他版本必须在部署完成后**手工替换版本文件并重启**，且部署日志中看不到这类变更。带来的直接后果：

- 交付过程被割裂成「平台部署 + 人工改造」，人工步骤无记录、无校验、不可重放。
- 部署日志无法反映实例最终状态的形成过程，失败无法归因。

## 3. 目标与成功标准

### 3.1 目标（G-）

| 编号 | 目标 | 对应决策 |
| --- | --- | --- |
| G-01 | 交付**通用**部署扩展步骤能力：任意游戏插件均可声明本游戏的部署扩展步骤，由主应用部署管线统一执行；主应用内不存在任何 dnf-tw 专用分支 | 决策 1 |
| G-02 | dnf-tw 可在部署向导选择目标版本，所选版本随实例配置落库，实例**第一次启动即为该版本**，全程无人工改文件、无人工重启 | 决策 3、4、9 |
| G-03 | 扩展过程与失败在**现有部署日志**中完整可见：阶段可辨识、每步开始/成功/失败/耗时可读、失败可归因到具体步骤 | 决策 5、8 |
| G-04 | 向后兼容零成本：未声明扩展步骤的游戏/插件，其部署行为（阶段序列、进度语义、状态转移、最终结果）与现状完全一致 | 决策 1、2、8 |

### 3.2 成功标准（KPI-）

| 编号 | 指标 | 分子 / 分母 | 数据源 | 刷新频率 | Owner | 目标值 |
| --- | --- | --- | --- | --- | --- | --- |
| KPI-01 | 指定版本部署的人工干预率 | 部署后仍需人工改文件或重启的实例数 / 选择非默认版本且部署成功的实例数 | 验收记录（AC-05）+ 部署日志 | 每次验收 | ProductManager | = 0 |
| KPI-02 | 扩展步骤日志可核对率 | 按**日志呈现契约**（§8.5）可机械判定「同一步骤的 开始 + 成功或失败 + 耗时」三项齐备的步骤数 / 已执行步骤总数；判定只依契约规定的标识，不得靠人工文本判读 | `GET /api/instances/{id}/deploy-progress` + 技术设计给出的呈现契约 | 实时 | @Architect | = 100%（**生效前提：呈现契约已由技术设计定稿并登记；契约未定稿前本条记为「不可测」，不得以人工阅读代替核对**） |
| KPI-03 | 非默认版本部署的非预期失败数 | 分子 = 分母中归因为**实现缺陷**的部署失败数；分母 = 「本次显式选择非默认版本」或「实例配置已存在 `deployVersion` 非默认值并重放」且 OP-02 真实资料齐备的部署总数。**排除项**（不进入分子，仍计入分母并逐条标注归因）：① BR-12 / §8.1 预期的「声明不可用」拦截失败；② OP-02 资料缺失或仅用占位模板的不可测部署；③ 外部资源自身问题（补丁 URL 不可达、`sha256` 与包实际摘要不符）。**每次失败必须归入实现缺陷 / 排除项① ② ③ 四类之一**，归类记录在验收记录中 | 同上 + `game_instance.run_status` + 验收记录归因列 | 每次验收 | ProductManager | = 0（**前置：OP-02 资料齐备；未齐备本期不考核，改按 RISK-06 记为不可测**） |
| KPI-04 | 无扩展声明游戏的部署回归通过率 | 既有部署相关自动化用例通过数 / 该范围用例总数 | `mvn test` + 前端 E2E | 每次合入 | @QA | = 100% |

> KPI-02 的「耗时」以部署日志可观测形式呈现即可，不要求前端展示独立计时控件；具体标识与字段由 §8.5 的呈现契约约定。
> KPI-03 不设成功率阈值：G-02 / AC-05 的要求是「正确资料下首启即目标版本、全程无人工干预」，任何实现缺陷导致的失败都不可接受，而 `≥ 90%` 既与该要求矛盾、又会把 BR-12 的**合规拦截失败**算成指标恶化（评审 SG-04）。

| FR-02 | 游戏无可用版本目录（无插件 / 插件未加载 / 目录为空 / 目录未通过 §8.1 校验）时，部署向导**不展示**「目标版本」选择项。**本条的「与现状等价」只在实例配置中不存在 `deployVersion` 键时成立**（首次部署，或该实例从未选过非默认版本）；若实例配置中已存在非默认 `deployVersion`（重部署重放路径，FR-13），目录不可用不得被降级成默认版本交付，改由 BR-12 拦截 | P0 | AC-02、AC-15、AC-20 |
| FR-03 | 用户所选**非默认**版本随实例配置落库到版本专用键 **`deployVersion`**（键名由本文档固定，§8.4），供重部署按同一配方重放；默认版本不写该键（三态见 §8.4） | P0 | AC-19 |
| FR-04 | 确认部署步骤的摘要中显示所选版本；未选择时显示「默认版本」 | P1 | AC-01 |

### 7.2 声明模型

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| FR-05 | 主应用提供按 `gameCode` 归属的扩展声明接口；插件可为**具体实例的配置（含所选版本）动态计算步骤集**；主应用不解释游戏语义 | P0 | AC-06、AC-18 |
| FR-06 | 步骤类型两类：`PATCH`（补丁替换）与 `SCRIPT`（脚本执行）；步骤集为**有序**清单，序号自 1 起 | P0 | AC-06 |
| FR-07 | 补丁步骤声明字段：`url`（必填）、`targetPath`（必填，实例相对路径）、`sha256`（可选）、`includePattern`（可选）、`fatal`（可选，默认致命）——字段口径见 §8.2 | P0 | AC-08、AC-11 |
| FR-08 | 脚本步骤声明字段：`label`、内容二选一（内嵌脚本正文 / `url` + `sha256` 拉取）、`position`（`host` 默认 / `container` 可选）、`fatal`（默认致命）；执行输出进部署日志——字段口径见 §8.3。**`position = container` 有生效前提**：FR-11 要求进入扩展阶段前实例处于停止，而 compose 类容器停止后 `exec` 无法执行（F-16），该组合是否合法由技术设计判定；判定不合法则 `container` 取值连同决策 7 的「容器内执行为步骤级可选项」**一并移出本期**，本期只交付 `position = host`（AC-13 同前提） | P0 | AC-12、AC-13 |
| FR-09 | 版本目录条目模型：`版号 → 镜像 tag（可选，缺省沿用默认）+ 补丁集 + 脚本集 + 目标路径`；`镜像 tag` 字段为框架通用能力保留，dnf-tw 本期不使用（无现成镜像，ADR-0029 Q9-a）。**`imageTag` 如何落到 compose 生成本期无现成机制**（F-09 模板无占位符、无结构化 image/tag 字段），落位方式登记为 §13 待改依赖交技术设计，AC-14 受同一前提约束 | P0 | AC-01、AC-14 |

## 8. 字段与数据口径

### 8.1 版本目录（Version Catalog）条目

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `versionId` | string | 是 | — | 同一游戏内唯一；非空；仅 `[A-Za-z0-9._-]` | 版号，即用户在向导看到的值 |
| `displayName` | string | 否 | `versionId` | — | 展示名（文案归 @Designer） |
| `imageTag` | string | 否 | 缺省 ⇒ 沿用游戏 compose 模板既有 tag | — | 框架保留字段；dnf-tw 本期不用（F-09） |
| `patches[]` | list | 否 | 空 | — | 见 §8.2 |
| `scripts[]` | list | 否 | 空 | — | 见 §8.3 |
| `default` | boolean | 否 | false | 同一游戏至多一条为 true | 标记默认版本条目 |

**默认版本语义**（BR-02）：目录中不存在扩展步骤、或用户未做选择的版本 = 默认版本 = 不执行扩展步骤 + 沿用 `dnf_tw.yml` compose 模板内既有镜像 tag 字面量。

**目录校验的时点与失败行为**（与 BR-12「声明不可用」同一口径，不另立判定）：

| 项 | 约定 |
| --- | --- |
| 校验时点 | **声明读取期**——每次部署（含重部署 / retry-deploy）按 `gameCode` + `deployType` 合并读取版本目录时（F-08 读时合并），逐条校验上表规则；不在部署向导进入步骤 2 之外另设校验时机，不做向导期 / 环境校验期前置探测（N-09） |
| 校验内容 | `versionId` 非空、同一游戏内唯一、字符集 `[A-Za-z0-9._-]`；`default = true` 至多一条；条目内 `patches[]`/`scripts[]` 各自字段符合 §8.2 / §8.3 的必填与互斥规则 |
| 不合规的失败行为 | 该游戏的版本目录整体判为**「声明不可用」**，按 BR-12 分两种情形处置，二者不得混淆：① 实例配置中**不存在** `deployVersion` 键（首次部署 / 从未选过非默认版本）→ 向导不展示选择项、不写键、部署照常按默认版本执行，并在部署日志记一条 `WARN`/`ERROR` 行说明「该游戏版本目录声明不合法，已按默认版本部署」；② 本次**显式选择**了非默认版本，或实例配置中**已存在**非默认 `deployVersion` 键 → **部署失败**、实例 `ERROR`、不启动、不交付，原因指名「版本声明不可用」 |
| 禁止行为 | 不得部分采纳（跳过不合规条目、执行其余条目）；不得静默改用默认版本条目交付（BR-12） |

### 8.2 补丁步骤（PATCH）

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `label` | string | 否 | 序号 + `PATCH` | — | 日志展示名 |
| `url` | string | 是 | — | 合法 http(s) URL | 补丁包来源（本期仅远端 URL，决策 6） |
| `targetPath` | string | 是 | — | 见 BR-05 | 实例相对路径（宿主安装目录或容器工作目录相对） |
| `sha256` | string | 否 | 不校验 | 64 位十六进制 | 完整性校验 |
| `includePattern` | string | 否 | 全部落位 | 逗号分隔 glob | 仅压缩包生效 |
| `format` | string | 否 | 按扩展名判定 | 沿用 `PatchFormat` 取值 | 压缩包格式 |
| `fatal` | boolean | 否 | **true** | — | 步骤致命性 |

**本期硬约束**：`headers` 不作为可声明字段（F-07 现有链路不承载）。若需要带鉴权头的补丁来源，另立需求，不混入本期。

### 8.3 脚本步骤（SCRIPT）

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `label` | string | 是 | — | 非空 | 日志展示名 |
| `content` | string | 与 `url` 二选一 | — | 二者必须恰有一个 | 内嵌脚本正文 |
| `url` + `sha256` | string | 与 `content` 二选一 | `sha256` 缺省不校验 | 合法 http(s) URL | 远端脚本 |
| `position` | enum(`host`\|`container`) | 否 | **`host`**（SSH） | `container` 有生效前提：FR-08 / FR-11 / F-16 / RISK-05（技术设计判定该组合不合法即移出本期） | 决策 7 |
| `fatal` | boolean | 否 | **true** | — | 步骤致命性 |

### 8.4 实例配置（`configInfo`）口径

**版本专用键定名 `deployVersion`。** 键名由本文档固定（评审 SG-01 / Leader 收敛），AC-19 等验收断言直接以它为对象；技术设计若需改名，走需求变更并同步本文档与 AC-19，**不在需求层保留「最终名待定」的开口**。

#### 8.4.1 键清单（同一扁平 map 内的共存关系）

| 键 | 写入方 | 含义 | 规则 |
| --- | --- | --- | --- |
| `deployVersion` | 部署向导提交（仅非默认版本时） | 用户所选**非默认**版本条目的 `versionId` | 值必须是该游戏版本目录中某条**非默认**条目的 `versionId`；不得与 §8.4.3 禁止清单中任何键同名（BR-07） |
| `gameVersion` | 前端既有代码 | 恒为 `undefined` 的**坏键** | 不得复用承载本期语义（F-11、RISK-10）；既不读写也不清理，另立需求处理 |
| `variables[].name` 各键 | 部署向导 | compose 变量值 | 语义不变，不与 `deployVersion` 互相覆盖 |
| `database` / `containerWorkDir` / `serviceName` | 适配器在 `DEPLOY` 阶段末回写并落库 | 系统保留键（F-15） | 由主应用侧生成，`deployVersion` 及 `variables[].name` 不得占用；声明期与提交期校验必须把它们纳入（BR-07） |

#### 8.4.2 三态与键行为（MF-01 要求逐态定义「是否写键、写什么值」）

| 态 | 触发条件 | 向导表现 | 是否写 `deployVersion` | 写入值 | 扩展阶段 | BR-12 是否可能触发 |
| --- | --- | --- | --- | --- | --- | --- |
| **S1 无目录** | 该游戏无可用版本目录（无插件 / 未加载 / 目录为空 / 未通过 §8.1 校验），**且实例配置中不存在 `deployVersion` 键**（首次部署或从未选过非默认版本） | 不展示版本选择项 | **不写**（载荷与现状等价，不出现空值、不写 `"default"`） | — | 不进入 | 否（FR-02「等价于现状」仅在此态成立） |
| **S2 缺省默认** | 目录可用，用户未做选择或显式选择默认版本条目 | 展示选择项，停在默认项（或显式选默认） | **不写**；若实例配置中已存在该键（历史上选过非默认版本后又改回默认），**提交时删除该键**（FR-13） | — | 不进入 | 否 |
| **S3 显式非默认** | 目录可用且用户选择非默认版本条目，或实例配置已存在非默认 `deployVersion` 被重放（FR-13） | 展示选择项并停在所选项；目录不可用而键存在时**不改选也无法展示**，走 BR-12 | **写** | 所选条目的 `versionId` | 进入（按目录条目步骤集） | **是**（目录 / 声明不可用即拦截） |

**不变式（实现与验收共用判定）**：`configInfo.deployVersion` 存在 **⇔** 该实例的部署目标是非默认版本。BR-12 的触发条件、FR-02 的「等价于现状」边界、AC-19/AC-20 的断言对象全部由此式判定，不需要读取任何界面状态或日志文本。

#### 8.4.3 撞键禁止清单（BR-07 校验对象）

`deployVersion` 在声明期与提交期都不得与以下键同名：① 该游戏 `variables[].name` 的任一取值（F-11 变量扁平铺顶部）；② 系统保留键 `database` / `containerWorkDir` / `serviceName`（F-15）；③ `gameVersion`（坏键，RISK-10）。

### 8.5 部署日志条目与「日志呈现契约」

沿用 `LogEntryVO{id,level,message,stage,time}` 与 `level ∈ INFO/WARN/ERROR/SUCCESS`。PRD 层约束（可观测要求）：

- 扩展阶段的每条日志 `stage` 值一致，且可与既有阶段值区分；
- 每步的「开始 / 成功或失败 / 耗时」三项对读者可见（FR-20）；
- 致命步骤失败行 `level = ERROR`，非致命步骤失败行 `level = WARN`。

**日志呈现契约（本文档不约定，交技术设计定）**：现有 `LogEntryVO` 既无步骤标识字段也无耗时字段（F-03），因此「同一步骤的三行如何归组」「耗时以何形式呈现」不能由 PRD 用 `message` 文本格式来钉。技术设计须给出并登记一份**日志呈现契约**，明确：① 步骤标识的承载位置（复用 `message` 内的固定前缀 / 扩展 VO 字段 / 其它，任选其一但须确定）；② 耗时的承载位置与单位；③ 三步行的归组规则。该契约是 **AC-03、AC-16、KPI-02 的核对前提**，未定稿或未登记时这三项一律记为「不可测」，禁止用人工阅读日志文本代替核对（评审 SG-05）。契约落点登记进 §13.2。

## 9. 状态机（实例运行状态视角）

| 时机 | 阶段 | 期望 `run_status` |
| --- | --- | --- |
| 提交部署 | `INIT`～`PORT_CHECK` | `INSTALLING`(5) |
| 资源就位 | `PRE_DEPLOY`、`DEPLOY` | `INSTALLING` |
| **进入扩展阶段** | 扩展 | `INSTALLING`；且实例进程/容器处于停止（FR-11） |
| 声明不可用且版本键已存在或被显式选择（BR-12 拦截） | 扩展阶段入口（读取目录时，§8.1 校验时点） | `ERROR`(4)，不执行任何步骤、不进入 `START` |

| 启动并复检通过 | `START` → `COMPLETE` | `RUNNING`(1)，**首启即目标版本** |

## 10. 业务规则（BR-）

| 编号 | 规则 | 依据 |
| --- | --- | --- |
| BR-01 | 版本目录与扩展步骤的唯一承载方是**游戏插件声明**（ADR-0008 读时合并体系）；主应用 `core/` 不得内置任何游戏专属版本表或版本判断逻辑 | 决策 1、9；ADR-0002 |
| BR-02 | 「默认版本」= 不执行扩展步骤 + 沿用游戏 compose 模板既有镜像 tag；用户未做选择即等价默认版本，行为与现状一致 | 决策 9；F-09；AC-02 |
| BR-03 | 版本选择是实例部署配方的一部分：换版本走「改实例配置 → 重新部署」，不提供部署后就地改版本的旁路 | 决策 4；FR-13 |
| BR-04 | 步骤致命性默认 `true`；非致命只能由声明侧显式给出，主应用不得推断或覆盖 | 决策 5 |
| BR-05 | 补丁 `targetPath` 必须是相对实例安装目录 / 容器工作目录的安全相对路径；拒绝绝对路径与目录越界（`..`）；落位口径沿用 `PatchInstallService` | ADR-0006；F-05 |
| BR-06 | 步骤必须按幂等设计：在已达目标状态的实例上重复执行须成功且结果不变；幂等性由声明方（插件）负责，主应用不判断「是否已做过」 | 决策 4 |
| BR-07 | `deployVersion` 与 compose 变量键、系统保留键共存于同一扁平 `configInfo`，因此它必须是独立专用键，且**声明期与提交期都校验**它不与 §8.4.3 禁止清单中任何键同名——禁止清单显式包含 `variables[].name` 各键（F-11）、适配器回写的系统保留键 `database` / `containerWorkDir` / `serviceName`（F-15）、坏键 `gameVersion`（RISK-10）。校验不通过即拒绝提交并给出可辨识原因，不得静默覆盖任何一方 | F-11、F-15；AC-19 |
| BR-08 | 主应用按声明顺序执行，不重排、不同实例内并发；`PATCH` 与 `SCRIPT` 混排时同样遵循声明顺序 | 决策 2 |
| BR-09 | 补丁步骤沿用既有资源约束：全局并发 3、每宿主机互斥、自动重试 2 次（5s/20s 退避）、备份保留 5 份 | F-05 |
| BR-10 | 扩展阶段不改变既有阶段语义：`HEALTH_CHECK` / `START` 的判定标准、`UPDATE_STATUS` 置 `STOPPED`、`COMPLETE = 100%` 均不变 | 决策 8 |
| BR-11 | 未声明扩展步骤的游戏与插件，其部署阶段序列、进度百分比语义、状态转移与结果必须与改造前等价（回归基线） | 决策 2、8；G-04 |
| BR-12 | **（派生规则，待 G0 确认）** **触发条件**（满足其一即触发；判定对象是 §8.4.2 不变式，可直接从实例配置读出，不依赖界面状态或日志文本）：① 本次部署**显式选择**了非默认版本；② 实例配置中**已存在**非默认 `deployVersion` 键（含 retry-deploy / 重部署的 FR-13 重放路径）。**触发后的行为**：只要该游戏版本目录不可用（插件未加载 / 声明接口异常 / 未通过 §8.1 校验 / 所选或已存的 `versionId` 不在目录中），部署必须失败、实例 `ERROR`、不启动、不交付，**不得静默按默认版本交付**，并在部署日志给出可辨识原因。**反向边界（不触发时）**：配置中不存在 `deployVersion` 键（S1 / S2）时，目录不可用只表现为「向导不展示选择项 + 按默认版本部署 + 一条 WARN/ERROR 日志行」，与现状等价（FR-02）。**为何只能在运行期拦**：本期不做向导期 / 环境校验期的版本可用性前置校验（N-09），扩展阶段入口是唯一判定点——这是 BR-12 存在的正当性依据。依据：决策 5 对「选了指定版本却交付错版本是最糟的静默失败」的判定；此项在 Issue 正文与 ADR 中未逐字出现，见 OP-06 | 决策 5（推论）；N-09；FR-02/FR-13/§8.1 |
| BR-13 | 部署日志为内存态，本期不作为长期审计证据；验收证据须在部署过程内当次采集 | 决策 8；F-03 |
| BR-14 | **多步骤失败的回滚边界（显式声明，不留给实现方各自解释）**：① 只有**失败步骤自身**的补丁改动被回滚（FR-19，`PatchInstallService` 的备份粒度即此边界）；② **此前已成功步骤的改动一律保留**，不做反向补偿；③ **脚本步骤没有任何回滚**，其副作用（改文件、改数据库、装包等）在部署失败后原样留在实例上；④ 实例随后置 `ERROR`（FR-17）；⑤ 收敛方式只有一条：修正配方后重新部署，由 BR-06 幂等 + FR-13 重放把实例推回目标状态。本期不提供撤销已执行步骤、回退默认版本或事务式全量回滚的能力（N-08） | 决策 5；FR-19；BR-06；评审 SG-07；AC-21 |

## 11. 空态 / 异常态 / 无权限态

| 场景 | 触发条件 | 系统表现 | 用户可见 |
| --- | --- | --- | --- |
| 无目录（S1） | 游戏无插件 / 插件未加载 / 目录为空 / 未通过 §8.1 校验，**且实例配置中无 `deployVersion` 键** | 向导不展示版本选择项；提交载荷不写该键；按默认版本部署，不进入扩展阶段 | 与现状无差异（AC-02）；目录不合法时部署日志多一条「版本目录声明不合法」说明行（§8.1） |
| 目录仅默认版本 | 只声明 `default = true` 条目 | 展示选择项但只有一个可选值；等价 S2，不写键 | 是否隐藏单值控件归 @Designer（OP-05） |
| 无扩展声明但有目录（S2） | 目录条目 `patches`/`scripts` 均空，或用户停在默认版本 | 走默认版本路径，不进入扩展阶段；不写键，若已存在该键则提交时删除（§8.4.2 S2） | 与现状无差异 |
| 声明不可用 + 目标是非默认版本（S3，BR-12） | ① 本次显式选择非默认版本，或 ② 实例配置已存在非默认 `deployVersion`（重部署 / retry-deploy 重放），而插件异常 / 接口异常 / 目录不合法 / `versionId` 不在目录中 | 扩展阶段入口判定 → 部署失败，实例 `ERROR`，不执行任何步骤、不启动 | 失败原因指名「版本声明不可用」，并指明是本次所选还是配置中既存键（BR-12，待 G0 确认；AC-20） |
| 向导不展示但键已存在 | 插件被卸载后对既有非默认版本实例重部署（目录不可用 + `deployVersion` 存在） | 同上一行：BR-12 拦截，**不得因界面上看不到版本项就按默认版本交付** | 日志指名「配置要求版本 X，但版本目录不可用」；用户可改选默认版本（删除键）后重新部署解锁 |
| 补丁下载失败 / sha256 不符 | URL 不可达、校验不通过 | 步骤失败 → 致命则部署失败；沿用补丁重试 | 日志含失败步骤与原因（AC-11） |
| 补丁目标回滚失败 | 备份不可用 | 部署失败，实例 `ERROR`，日志标注回滚结果 | 需人工介入（AC-09） |
| 多步骤中途失败 | 前序步骤已成功、后续步骤致命失败 | 失败步骤自身补丁回滚；前序已成功步骤改动与脚本副作用保留；实例 `ERROR` | 边界见 BR-14；恢复方式是修正配方后重新部署（AC-21） |
| 脚本非零退出 | `exitCode ≠ 0` | 判失败，按致命性处理 | 日志含 exitCode 与输出（AC-12）；既有容器通道丢弃 exitCode，须先改造（F-16、§13） |
| 脚本超时 | 超过 `timeoutMs` | 判失败，按致命性处理 | 阈值取值待 OP-04 |
| 容器内执行 + 实例已停止 | 声明 `position = container` 的步骤，而 FR-11 要求进入扩展阶段前实例停止（compose 停实例后 `exec` 无法执行，F-16） | **该组合能否成立由技术设计判定（RISK-05）**：判不合法则 `position = container` 与「容器内执行为步骤级可选项」一并移出本期（FR-08）；判合法则按合法结果执行 | 判定前 AC-13 不执行（有生效前提）；判定后统一 |
| 宿主机 SSH 不可达 | 主机凭证失效 | 步骤失败 → 致命则部署失败 | 日志含主机与原因 |
| 未登录 / 凭证过期 | 调用部署或日志接口 | HTTP 401 / 403 | 沿用平台既有登录页跳转，无新增权限态（§4.2） |

## 12. 验收标准（AC-）

### 12.1 用例

> **「生效前提」约定**：AC-13 / AC-14 / AC-20（以及 KPI-02、AC-03、AC-16 的核对方式）各有一个不在本文档判定范围内的前提（分别对应 RISK-05、imageTag 机制、BR-12 是否采纳、§8.5 呈现契约）。前提成立才执行该条；前提不成立时该条记为「本期不验收」或「不可测」，**禁止用相邻路径或人工判读冒充通过**（评审 MF-02 方案 b）。

| 编号 | 前置 | 操作 | 预期结果 |
| --- | --- | --- | --- |
| AC-01 | dnf-tw 插件声明了含 ≥2 条目的版本目录 | 打开部署向导，选 dnf-tw + docker-compose | 出现目标版本选择项，选项与目录 `versionId` 一致，默认项为默认版本；确认部署摘要显示所选版本（FR-01/04/09） |
| AC-02 | 同上（目录可用） | 不做版本选择（保持默认，即 S2）提交部署 | 无扩展阶段步骤行；阶段序列与现状一致；实例以默认版本运行；`configInfo` 中**不存在** `deployVersion` 键（§8.4.2 S2「不写」），其余键与现状一致（FR-02/BR-02） |
| AC-03 | 选择非默认版本 | 提交部署并轮询 `GET /api/instances/{id}/deploy-progress` | 日志出现扩展阶段（`stage` 可区分）；每个已执行步骤的「开始 / 成功或失败 / 耗时」三项按**§8.5 日志呈现契约**可机械判定齐备。**核对脚本以契约规定的标识为对象；契约未登记时本条记为「不可测」，不得以人工阅读文本代替**（FR-20/KPI-02） |

| AC-05 | 选择非默认版本且补丁生效 | 观察部署结束后的实例 | 实例进入 `RUNNING` 且**首次启动即目标版本**；全程无人工改文件、无人工重启；`HEALTH_CHECK`/`START` 判定标准未被绕过（FR-16/G-02） |

| AC-07 | 实例已以非默认版本部署完成（`configInfo.deployVersion` 存在）且目录仍可用 | 改一次无关配置后重新部署（或走 retry-deploy），**本次不改选版本**（界面停在既存值即算未改选） | 扩展阶段再次执行**同一**步骤集并重放成功；`deployVersion` 读取自 `configInfo` 沿用，不依赖用户本次是否重新点选，也不被本次提交清空或改写（FR-13/BR-03）。目录不可用而键存在的分支不属本条（那是失败路径，见 AC-20(b)） |
| AC-08 | 声明一个致命补丁步骤并使其失败（URL 不可达） | 部署 | 其后步骤不执行；部署判失败；实例 `ERROR`；未进入 `START`；日志指明失败步骤标识与原因（FR-17） |

| AC-11 | 补丁步骤声明 `sha256` 且值与包实际摘要不符 | 部署 | 步骤判失败；致命性为 true 时部署失败（FR-07/14） |
| AC-12 | 脚本步骤 `position = host`（缺省）且输出可见内容 | 部署 | 经宿主机 SSH 执行；`stdout`/`stderr`/exitCode 进部署日志；`exitCode ≠ 0` 判失败（FR-08/15） |

| AC-14 | 版本目录条目声明了非默认 `imageTag` | 部署 | **生效前提（两条同时成立才执行本条）**：① 技术设计给出 `imageTag` 落到 compose 生成的机制（§13 待改依赖；F-09 模板无占位符、无结构化 image/tag 字段）；② 存在可承载声明的插件载体——第二个游戏插件或 dnf-tw 桩插件，是否本期交付随 OP-01 一并裁决。前提成立 → 生成的 compose 使用所声明 tag，未声明时模板文本不变（FR-09）；任一前提不成立 → 本条记为「本期不验收」，不得以文本比对冒充 |
| AC-15 | 未声明扩展步骤的游戏（例：l4d2 或任一 linuxgsm 游戏） | 走完整部署 | 阶段序列、状态转移、进度百分比语义、日志结构、最终结果与改造前逐项目一致（G-04/BR-11） |
| AC-16 | 扩展阶段执行中 | 观察前端部署日志面板 | 用户可辨识当前处于扩展阶段、以及正在执行的是哪一步（步骤标签）；无需新接口即达成（FR-20）。**「哪一行属于哪一步骤」的判读方式依赖 §8.5 日志呈现契约**；契约未登记时本条与 AC-03 同样记为「不可测」 |

## 14. 风险（RISK-）

| 编号 | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| RISK-01 | 扩展阶段引入「停实例 → 补丁/脚本 → 再启动」的固定成本 | 部署总耗时上升，慢补丁来源会拉长反馈；进度条停滞观感 | 每步耗时可观测（FR-20）；超时声明（§8.3）；耗时阈值上线后据实评估（KPI-02 先建核对能力） |
| RISK-02 | `headers`/`includePattern` 在任务 payload 序列化时丢失（F-07 有行号证据） | 决策 6 承诺的 `includePattern` 直接复用即失效；本期已排除 `headers` | 列入依赖，要求设计侧补齐字段透传或改用同链路内执行；AC-11 之外补测 includePattern 落位 |
| RISK-03 | `install()` 异步语义与扩展阶段「阻塞 + 过程进日志」冲突（F-06） | 若设计不解决，日志只有开始/结束两行，KPI-02 无法达标 | FR-12/FR-20 作为验收硬门；设计需给出进度桥接或同步通道 |
| RISK-04 | 部署日志内存态（F-03） | 进程重启即丢证据，失败难复现；审计不可用 | BR-13 明确限制；验收当次采集（§16 L-01）；落库另立需求（N-03） |
| RISK-05 | 「扩展前先停实例」对 compose 类适配器语义不清（`stop` 与 `down` 的数据/网络后果不同，`:395` vs `:556`），停失败无裁决；**且停实例与 `position = container` 在既有实现下互斥**——容器停止后 `compose exec` 必然失败（F-16） | 可能引发数据目录/卷状态或容器名冲突；容器内执行这一半能力可能整体落空 | 交 @Architect 定义「停止状态」的可观察结果与停失败处置（FR-11）。**统一口径（本文档五处一致：FR-08 / FR-11 / §8.3 / §11 / AC-13）**：技术设计若判定「停实例 + 容器内执行」组合不合法，则 `position = container` 连同决策 7 的「容器内执行为步骤级可选项」**移出本期**，本期只交付 `position = host`，AC-13 记为「本期不验收」——移出属需求范围收缩，须回写本文档并记修订记录，不得由实现侧静默取舍 |
| RISK-06 | OP-02 资料缺失 | 无法端到端验证补丁与脚本，AC-05/09/11/12/13 与 KPI-03 不可测 | 本期降级为「框架 + 版本目录占位模板」，并在验收记录标注不可测项（禁止编造资料）；KPI-03 已按「非预期失败数 = 0」重写，其分母要求资料齐备（§3.2） |

| RISK-08 | 脚本步骤扩大插件侧可执行的命令面（宿主机 root 用户或容器内任意 shell） | 越权、误删、不可审计 | 声明只出自插件代码（非运行时可配）；不新增用户输入面；要求设计保留命令文本日志（沿用 F-13 通道既有 INFO 记录） |
| RISK-09 | retry-deploy 既有路径先 `adapter.uninstall(...)` 再部署（F-04），与扩展阶段先后关系未覆盖 | 重部署可能落在已被卸载的状态上；也可能连带清掉 `configInfo`，使 FR-13 重放与 §8.4.2 不变式失效 | 交 @Architect 明确；FR-13 只约束「必须重放且不丢键」 |
