## 1. 一句话定义

在部署流程中新增由游戏插件声明、由主应用部署管线执行的**部署扩展步骤**（补丁替换 + 脚本执行），使用户可以在部署向导中选择目标版本（首个用例为 dnf-tw），实例**第一次启动即为所选版本**，全过程与失败结果在部署日志中可见可判。

---

## 2. 背景与问题

### 2.1 问题

部署流程今天是「部署即终态」：部署动作完成即交付，没有部署期自动化能力。以 dnf-tw 为例，上游镜像只提供默认版本，要部署其他版本必须在部署完成后**手工替换版本文件并重启**，且部署日志中看不到这类变更。带来的直接后果：

- 交付过程被割裂成「平台部署 + 人工改造」，人工步骤无记录、无校验、不可重放。
- 部署日志无法反映实例最终状态的形成过程，失败无法归因。

| KPI-02 | 扩展步骤日志可核对率 | 按**日志呈现契约**（§8.5）可机械判定「同一步骤的 开始 + 成功或失败 + 耗时」三项齐备的步骤数 / 已执行步骤总数；判定只依契约规定的标识，不得靠人工文本判读 | `GET /api/instances/{id}/deploy-progress` + 技术设计给出的呈现契约 | 实时 | @Architect | = 100%（**生效前提：呈现契约已由技术设计定稿并登记；契约未定稿前本条记为「不可测」，不得以人工阅读代替核对**） |
| KPI-03 | 非默认版本部署的非预期失败数 | 分子 = 分母中归因为**实现缺陷**的部署失败数；分母 = 「本次显式选择非默认版本」或「实例配置已存在 `deployVersion` 非默认值并重放」且 OP-02 真实资料齐备的部署总数。**排除项**（不进入分子，仍计入分母并逐条标注归因）：① BR-12 / §8.1 预期的「声明不可用」拦截失败；② OP-02 资料缺失或仅用占位模板的不可测部署；③ 外部资源自身问题（补丁 URL 不可达、`sha256` 与包实际摘要不符）。**每次失败必须归入实现缺陷 / 排除项① ② ③ 四类之一**，归类记录在验收记录中 | 同上 + `game_instance.run_status` + 验收记录归因列 | 每次验收 | ProductManager | = 0（**前置：OP-02 真实资料齐备。G0 已裁决本期交付「框架 + 占位模板」，即本期为缺口期，本条不考核、记「不可测」（§17 L-02 / BR-15 ③）；真实资料填充后自动转为可考核，无需改动本文口径**） |
| KPI-04 | 无扩展声明游戏的部署回归通过率 | 既有部署相关自动化用例通过数 / 该范围用例总数 | `mvn test` + 前端 E2E | 每次合入 | Tester | = 100% |

> KPI-02 的「耗时」以部署日志可观测形式呈现即可，不要求前端展示独立计时控件；具体标识与字段由 §8.5 的呈现契约约定。
> KPI-03 不设成功率阈值：G-02 / AC-05 的要求是「正确资料下首启即目标版本、全程无人工干预」，任何实现缺陷导致的失败都不可接受，而 `≥ 90%` 既与该要求矛盾、又会把 BR-12 的**合规拦截失败**算成指标恶化（评审 SG-04）。
> **本期（G0 裁决后的缺口期）KPI 考核范围**：可考核 = KPI-02（**其前提已随 §8.5 呈现契约定稿登记而成立 ⇒ 自 v0.6 起无条件考核，D-P09**）、KPI-04；记「不可测」= KPI-01、KPI-03（两者对象均为 dnf-tw 真实版本部署，见 §17 L-02）。缺口期内，**KPI 分母中的「非默认版本部署」可由最小桩插件 + 验收夹具承载**（§5.1.1 验收资产），这类结果只计入框架类判定，**不得计入 KPI-01 / KPI-03**（BR-15 ②）。
>
> **KPI-02 分母的精确口径（v0.6 按 D-P09 补，来源 = design.md §14.6 规则 2 + §10 V-08）**：分母 = **该次部署中 `stepId` 非空的步骤去重计数**，**不含阶段级行**（进入 / 交棒 / 停实例 / BR-12 拦截 / 目录不合法说明 / 收尾 / 阶段完成这些行没有 `stepId`）。这不是抠字眼：阶段级行**按构造永远不满足**「恰一条 `START` + 恰一条终态」，把它们算进分母，一份完全正确的实现最高也只能得 n/(n+1)，**本 KPI 的 100% 就在字面上不可满足**。上表「已执行步骤总数」自此按本注读。

## 5. 范围与非范围

### 5.1 本期范围

> 本节口径来自 G0 裁决：OP-01 = **是**（第 3 项 + §5.1.1 新增模块行）、OP-02 = **框架 + 占位模板，显式标注不可上线**（第 4 项 + FR-23 / BR-15）、OP-03 = **本期不做**（已回填为 §5.2 **N-10**）。落点逐条见 §13.4。

1. 通用部署扩展步骤框架：声明模型（版本目录 + 补丁步骤 + 脚本步骤）、执行管线（部署扩展阶段）、日志呈现、失败语义。
2. 部署向导的目标版本选择；选择结果随 `configInfo` 落库（键 `deployVersion`，§8.4）；重部署按同一配方重放（键的存续性含**与部署无关的写路径**，BR-16 / AC-27）。
3. **新建最小 `plugin-dnf-tw` 插件模块**（OP-01 裁决为「是」），承载 dnf-tw 的版本目录与补丁 / 脚本声明，是 ADR-0008 声明机制（F-08）的首个使用方；模块布局参照 `plugin-l4d2`（F-17），**不含插件前端**（本期无 dnf-tw 专属页面需求，也不得新增 standalone 模式，ADR-0003）。
4. **dnf-tw 版本目录以「占位模板」形式交付并显式标注不可上线**（OP-02 裁决）：模板随模块交付，**未填入人类 Owner 提供的真实资料即不对外生效**（读取结果＝空目录 → S1，§8.4.2）；真实资料到位后**只替换目录内容即生效，不得要求改动框架代码或声明接口**（FR-23、BR-15）。
5. dnf-tw 游戏元数据 `dnf_tw.yml` 的镜像 tag 与既有 `variables` 保持现状（默认版本路径），本期不因本需求改动（BR-02）。

**新增模块对既有工程约定的符合性**（不是新的产品决策，只是范围落位）：`plugin-dnf-tw` 是继 `plugin-l4d2` 之后的**第二个**游戏插件模块——其插件配置由自身 `@ConfigurationProperties` 默认值自负、其扩展资源表由 ExtensionClient 按 `ext_plugin_{pluginId}_{resource}` 模式自管，主应用 `core/` 不得出现以 dnf-tw 游戏码为条件的业务分支（ADR-0002、BR-01、G-01；核对口径见 AC-23 ③）。

## 8. 字段与数据口径

### 8.1 版本目录（Version Catalog）条目

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `versionId` | string | 是 | — | 同一游戏内唯一；非空；仅 `[A-Za-z0-9._-]` | 版号，即用户在向导看到的值 |
| `displayName` | string | 否 | `versionId` | — | 展示名（文案归 @Designer） |
| `imageTag` | string | 否 | 缺省 ⇒ 沿用游戏 compose 模板既有 tag | — | 框架保留字段；dnf-tw 本期不用（F-09） |
| `patches[]` | list | 否 | 空 | — | 见 §8.2 |
| `scripts[]` | list | 否 | 空 | — | 见 §8.3 |
| `default` | boolean | 否 | false | 同一游戏至多一条为 true | 标记默认版本条目 |

**默认版本语义**（BR-02）：目录中不存在扩展步骤、或用户未做选择的版本 = 默认版本 = 不执行扩展步骤 + 沿用 `dnf_tw.yml` compose 模板内既有镜像 tag 字面量。

**目录校验的时点与失败行为**（与 BR-12「声明不可用」同一口径，不另立判定）：

| 项 | 约定 |
| --- | --- |
| 校验时点 | **声明读取期**——每次部署（含重部署 / retry-deploy）按 `gameCode` + `deployType` 合并读取版本目录时（F-08 读时合并），逐条校验上表规则；不在部署向导进入步骤 2 之外另设校验时机，不做向导期 / 环境校验期前置探测（N-09） |
| 校验内容 | **基础项**：`versionId` 非空、同一游戏内唯一、字符集 `[A-Za-z0-9._-]`；`default = true` 至多一条；条目内 `patches[]`/`scripts[]` 各自字段符合 §8.2 / §8.3 的必填与互斥规则。**v0.6 按 D-P05② 增补五条**（来源 = design.md §8.1 + §16.3 的 N1…N5，任一不合规即整目录判「声明不可用」、**禁止部分采纳**）：**N1** 判定通道唯一 = `game_metadata` 表快照，且与实际部署取数**同一数据源、同一取值路径**（插件经 `getDeployConfigs()` 声明的 `variables` / `composeTemplate` **不参与**校验，见 F-19）；**N2** 该 deployType 的表侧模板必须含 `${PLATFORM_IMAGE_TAG` 占位符字面量，否则声明了 `imageTag` 就是静默无效；**N3** 镜像 tag 与变量默认值的格式校验（字符集与长度）；**N4** `timeoutMs` 必须落在 §8.3 的合法区间内，且 `position` 本期只接受 `host`；**N5** **deployType 支持集合**——集合外（含 plain `docker`）带任何步骤或 `imageTag` 的目录即不合法（FR-11 / D-P15）。**五条均是「不合法」而不是「忽略该字段继续」** |
| 不合规的失败行为 | 该游戏的版本目录整体判为**「声明不可用」**，按 BR-12 分两种情形处置，二者不得混淆：① 实例配置中**不存在** `deployVersion` 键（首次部署 / 从未选过非默认版本）→ 向导不展示选择项、不写键、部署照常按默认版本执行，并在部署日志记一条 `WARN`/`ERROR` 行说明「该游戏版本目录声明不合法，已按默认版本部署」；② 本次**显式选择**了非默认版本，或实例配置中**已存在**非默认 `deployVersion` 键 → **部署失败**、实例 `ERROR`、不启动、不交付，原因指名「版本声明不可用」 |
| 禁止行为 | 不得部分采纳（跳过不合规条目、执行其余条目）；不得静默改用默认版本条目交付（BR-12） |

#### 8.4.1 键清单（同一扁平 map 内的共存关系）

| --- | --- | --- | --- | --- | --- | --- |
| **S1 无目录** | 该游戏无可用版本目录（无插件 / 未加载 / 目录为空 / 未通过 §8.1 校验），**且实例配置中不存在 `deployVersion` 键**（首次部署或从未选过非默认版本） | 不展示版本选择项 | **不写**（载荷与现状等价，不出现空值、不写 `"default"`） | — | 不进入 | 否（FR-02「等价于现状」仅在此态成立） |

**不变式（实现与验收共用判定）**：`configInfo.deployVersion` 存在 **⇔** 该实例的部署目标是非默认版本。BR-12 的触发条件、FR-02 的「等价于现状」边界、AC-19/AC-20 的断言对象全部由此式判定，不需要读取任何界面状态或日志文本。**该式的成立前提是「键不会被无关写路径静默删掉」，这一前提由 BR-16 守住（现状缺陷见 F-18 / AC-27）——否则不变式会在用户未做任何版本操作的情况下翻转。**

#### 8.4.3 撞键禁止清单（BR-07 校验对象）

`deployVersion` 在提交期不得与以下键同名：① 该游戏 `variables[].name` 的任一取值（F-11 变量扁平铺顶部）；② 系统保留键 `database` / `containerWorkDir` / `serviceName`（F-15）；③ `gameVersion`（坏键，RISK-10）。

**时点口径（v0.7 收敛，依据 = Leader 裁定评论 `01a0cf20` §三）**：撞键校验**只在提交期**做一次。v0.6 之前本行写作「声明期与提交期都校验」，而声明期那一半从来没有承载入口——§8.1「校验内容」行的五条 N1…N5 不含「`deployVersion` 与 `variables[].name` 同名 ⇒ 目录不合法」这一条，技术设计也不补：**补了会给「目录不合法」多出一个判据来源**，而目录的唯一读者已钉在 design.md §16.3 的 `DeployVersionCatalogService`（N1…N5 属 G1 基线，动它须回头重跑 G1）。本段只登记时点，**不改判定对象与处置后果**：清单四类成员（`variables[].name` 各键 / `database` / `containerWorkDir` / `serviceName` / `gameVersion`）、BR-07 的「拒绝提交 + 可辨识原因 + 不得静默覆盖任何一方」、AC-19 的逐键断言全部一字未动。下一段 `PLATFORM_IMAGE_TAG` 的**声明期保留键**归属与本段无关，那是「谁的键、值由谁写」的问题，不是撞键校验的时点问题。

**`PLATFORM_IMAGE_TAG` 不进本清单**（D-P05①，v0.6 订正——v0.5 及之前把它当撞键风险对待是错的）：它是**声明期保留键**，会作为 `variables[]` 的一项合法出现在提交载荷里，进禁止清单等于把 AC-14 的正向路径判 400 拒掉。其口径改由声明期约束承担：**该键的提交值不参与任何判定，值一律由平台在部署配置组装时写入**（design.md §14.4.2、§8.1 的 N2/N3）；用户或插件在 `configInfo` 里给的值不生效、也不报错——这是「平台写、不由用户填」的显式取舍，不是漏校验。

### 8.5 部署日志条目与「日志呈现契约」

沿用 `LogEntryVO{id,level,message,stage,time}` 与 `level ∈ INFO/WARN/ERROR/SUCCESS`。PRD 层约束（可观测要求）：

- 扩展阶段的每条日志 `stage` 值一致（常量 `EXTENSION`），且可与既有阶段值区分；**该判据的取值域是「扩展阶段内的行」，不是部署日志的全部行**（v0.6 按 Leader 裁定 `01a0c4d8` 写明，来源 = design.md §14.6 `stage` 行 + §10 V-08）——既有阶段（`INIT`…`DEPLOY` / `HEALTH_CHECK`…`COMPLETE`）的行本就该取各自的阶段名，把全部行并进这条判据会把一份正确的实现判成违规。**两类只在扩展阶段入口判定产出的条件行分别归属、不共用一个取值**：**① BR-12 拦截行 = 扩展阶段的行**（它发生在扩展阶段入口，该次部署的阶段以「入口判定不合法」短暂成立：产进入行 + 拦截行即终止，故界面上「本次进过扩展阶段」成立、阶段带渲染）；**②「目录不合法 → 按默认版本继续」那条说明行 = 它实际发生所在的既有阶段的行**（无键即不拦截、步骤集为空 ⇒ 扩展阶段整体不存在，本期该点承在 `DEPLOY` 上；**钉的是「行归它实际发生的阶段」这条判据，不是某个阶段名的字面量**，实现若把读目录判定前移则随之而移）；
- 每步的「开始 / 成功或失败 / 耗时」三项对读者可见（FR-20）；
- 致命步骤失败行 `level = ERROR`，非致命步骤失败行 `level = WARN`；**`level → 视觉映射` 的判据 = 前端归一化、后端取值集合不变**（D-P06 已定稿：`SUCCESS`/`WARN`/`ERROR`/`INFO` 四类不得再同色同图标；既有代码另有 `warn` 与 `warning` 两种写法，归一化须同时认——design.md §14.9）。

**日志呈现契约（已由技术设计定稿并登记，本节自此是引用、不是待办）**：现有 `LogEntryVO` 既无步骤标识字段也无耗时字段（F-03），因此「同一步骤的三行如何归组」「耗时以何形式呈现」不能由 PRD 用 `message` 文本格式来钉。技术设计已给出并登记该契约（**design.md §14.6**；§14.2 对应行状态改「已定稿」），取**扩展 VO 字段**方案：① 步骤标识由新增 `stepId`（`E-<序号>`，同一次部署内唯一）承载，归组主键是**字段**而非文本前缀；② 耗时由新增 `elapsedMs` 承载，**单位毫秒、权威值只在 VO 上**，秒值只出现在渲染层；③ 归组与「三项齐备」的判据 = 同一 `stepId` 下**恰一条 `START` + 恰一条终态（`SUCCESS`/`FAILURE`）且该终态行 `elapsedMs` 非空**（KPI-02 的分母只数**非空** `stepId`，`stepId == null` 的阶段级行不进分母——口径见 design.md §14.6 规则 2）；④ 另有 `stepIndex`/`stepTotal`、`stepLabel`/`stepType`、`stepEvent`、`exitCode` 四个字段位，六个字段位在 VO 上展开为 8 个属性。该契约是 **AC-03、AC-16、KPI-02 的核对前提，三者自此可考核**——v0.5 之前挂的「契约未登记时记不可测」条件句随本段成立而解除（D-P09 / D-P12，另两处同族条件句一并改述，见 §11.1 与 §13.1 引言）。**核对一律机械读字段，禁止用人工阅读日志文本代替核对**（评审 SG-05）。**承载位分工须同批读到（D-P17）**：`stdout` / `stderr` **只进 `message` 文本、不参与任何机械判据**，其可见性核对与 AC-12 的失败判定**分离登记**——不得把 FR-15 的「输出进日志」在验收时读成对文本的匹配要求；`exitCode` 有独立字段，「`exitCode ≠ 0` 判失败」是机械判据，AC-12 自此是该契约的读者之一。

## 9. 状态机（实例运行状态视角）

| 时机 | 阶段 | 期望 `run_status` |
| --- | --- | --- |

### 13.1 用例
