## 1. 一句话定义

在部署流程中新增由游戏插件声明、由主应用部署管线执行的**部署扩展步骤**（补丁替换 + 脚本执行），使用户可以在部署向导中选择目标版本（首个用例为 dnf-tw），实例**第一次启动即为所选版本**，全过程与失败结果在部署日志中可见可判。

---

## 2. 背景与问题

### 2.1 问题

部署流程今天是「部署即终态」：部署动作完成即交付，没有部署期自动化能力。以 dnf-tw 为例，上游镜像只提供默认版本，要部署其他版本必须在部署完成后**手工替换版本文件并重启**，且部署日志中看不到这类变更。带来的直接后果：

- 交付过程被割裂成「平台部署 + 人工改造」，人工步骤无记录、无校验、不可重放。
- 部署日志无法反映实例最终状态的形成过程，失败无法归因。

## 5. 范围与非范围

### 5.1 本期范围

> 本节口径来自 G0 裁决：OP-01 = **是**（第 3 项 + §5.1.1 新增模块行）、OP-02 = **框架 + 占位模板，显式标注不可上线**（第 4 项 + FR-23 / BR-15）、OP-03 = **本期不做**（已回填为 §5.2 **N-10**）。落点逐条见 §13.4。

1. 通用部署扩展步骤框架：声明模型（版本目录 + 补丁步骤 + 脚本步骤）、执行管线（部署扩展阶段）、日志呈现、失败语义。
2. 部署向导的目标版本选择；选择结果随 `configInfo` 落库（键 `deployVersion`，§8.4）；重部署按同一配方重放（键的存续性含**与部署无关的写路径**，BR-16 / AC-27）。
3. **新建最小 `plugin-dnf-tw` 插件模块**（OP-01 裁决为「是」），承载 dnf-tw 的版本目录与补丁 / 脚本声明，是 ADR-0008 声明机制（F-08）的首个使用方；模块布局参照 `plugin-l4d2`（F-17），**不含插件前端**（本期无 dnf-tw 专属页面需求，也不得新增 standalone 模式，ADR-0003）。
4. **dnf-tw 版本目录以「占位模板」形式交付并显式标注不可上线**（OP-02 裁决）：模板随模块交付，**未填入人类 Owner 提供的真实资料即不对外生效**（读取结果＝空目录 → S1，§8.4.2）；真实资料到位后**只替换目录内容即生效，不得要求改动框架代码或声明接口**（FR-23、BR-15）。
5. dnf-tw 游戏元数据 `dnf_tw.yml` 的镜像 tag 与既有 `variables` 保持现状（默认版本路径），本期不因本需求改动（BR-02）。

**新增模块对既有工程约定的符合性**（不是新的产品决策，只是范围落位）：`plugin-dnf-tw` 是继 `plugin-l4d2` 之后的**第二个**游戏插件模块——其插件配置由自身 `@ConfigurationProperties` 默认值自负、其扩展资源表由 ExtensionClient 按 `ext_plugin_{pluginId}_{resource}` 模式自管，主应用 `core/` 不得出现以 dnf-tw 游戏码为条件的业务分支（ADR-0002、BR-01、G-01；核对口径见 AC-23 ③）。

| `scripts[]` | list | 否 | 空 | — | 见 §8.3 |
| `default` | boolean | 否 | false | 同一游戏至多一条为 true | 标记默认版本条目 |

**默认版本语义**（BR-02）：目录中不存在扩展步骤、或用户未做选择的版本 = 默认版本 = 不执行扩展步骤 + 沿用 `dnf_tw.yml` compose 模板内既有镜像 tag 字面量。

**目录校验的时点与失败行为**（与 BR-12「声明不可用」同一口径，不另立判定）：

| 项 | 约定 |
| --- | --- |
| 校验时点 | **声明读取期**——每次部署（含重部署 / retry-deploy）按 `gameCode` + `deployType` 合并读取版本目录时（F-08 读时合并），逐条校验上表规则；不在部署向导进入步骤 2 之外另设校验时机，不做向导期 / 环境校验期前置探测（N-09） |
| 校验内容 | `versionId` 非空、同一游戏内唯一、字符集 `[A-Za-z0-9._-]`；`default = true` 至多一条；条目内 `patches[]`/`scripts[]` 各自字段符合 §8.2 / §8.3 的必填与互斥规则 |
| 不合规的失败行为 | 该游戏的版本目录整体判为**「声明不可用」**，按 BR-12 分两种情形处置，二者不得混淆：① 实例配置中**不存在** `deployVersion` 键（首次部署 / 从未选过非默认版本）→ 向导不展示选择项、不写键、部署照常按默认版本执行，并在部署日志记一条 `WARN`/`ERROR` 行说明「该游戏版本目录声明不合法，已按默认版本部署」；② 本次**显式选择**了非默认版本，或实例配置中**已存在**非默认 `deployVersion` 键 → **部署失败**、实例 `ERROR`、不启动、不交付，原因指名「版本声明不可用」 |
| 禁止行为 | 不得部分采纳（跳过不合规条目、执行其余条目）；不得静默改用默认版本条目交付（BR-12） |

### 8.2 补丁步骤（PATCH）

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `label` | string | 否 | 序号 + `PATCH` | — | 日志展示名 |
| `url` | string | 是 | — | 合法 http(s) URL | 补丁包来源（本期仅远端 URL，决策 6） |
| `targetPath` | string | 是 | — | 见 BR-05 | 实例相对路径（宿主安装目录或容器工作目录相对） |
| `sha256` | string | 否 | 不校验 | 64 位十六进制 | 完整性校验 |
| `includePattern` | string | 否 | 全部落位 | 逗号分隔 glob | 仅压缩包生效 |
| `format` | string | 否 | 按扩展名判定 | 沿用 `PatchFormat` 取值 | 压缩包格式 |
| `fatal` | boolean | 否 | **true** | — | 步骤致命性 |

**本期硬约束**：`headers` 不作为可声明字段（F-07 现有链路不承载）。若需要带鉴权头的补丁来源，另立需求，不混入本期。

### 8.3 脚本步骤（SCRIPT）

| 字段 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `label` | string | 是 | — | 非空 | 日志展示名 |
| `content` | string | 与 `url` 二选一 | — | 二者必须恰有一个 | 内嵌脚本正文 |
| `url` + `sha256` | string | 与 `content` 二选一 | `sha256` 缺省不校验 | 合法 http(s) URL | 远端脚本 |
| `position` | enum(`host`\|`container`) | 否 | **`host`**（SSH） | `container` 有生效前提：FR-08 / FR-11 / F-16 / RISK-05（技术设计判定该组合不合法即移出本期） | 决策 7 |
| `fatal` | boolean | 否 | **true** | — | 步骤致命性 |
| `timeoutMs` | integer | 否 | 待定（OP-04） | > 0 | 步骤超时。**既有容器执行通道超时硬编码 60s 且丢弃退出码（F-16）**，`timeoutMs` 与 FR-15 的 exitCode 判定须先改造该通道（§14.2 待改依赖） |

### 8.4 实例配置（`configInfo`）口径

**版本专用键定名 `deployVersion`。** 键名由本文档固定（评审 SG-01 / Leader 收敛），AC-19 等验收断言直接以它为对象；技术设计若需改名，走需求变更并同步本文档与 AC-19，**不在需求层保留「最终名待定」的开口**。

#### 8.4.1 键清单（同一扁平 map 内的共存关系）

| 键 | 写入方 | 含义 | 规则 |
| --- | --- | --- | --- |
| `deployVersion` | 部署向导提交（仅非默认版本时） | 用户所选**非默认**版本条目的 `versionId` | 值必须是该游戏版本目录中某条**非默认**条目的 `versionId`；不得与 §8.4.3 禁止清单中任何键同名（BR-07） |
| `gameVersion` | 前端既有代码 | 恒为 `undefined` 的**坏键** | 不得复用承载本期语义（F-11、RISK-10）；既不读写也不清理，另立需求处理 |
| `variables[].name` 各键 | 部署向导 | compose 变量值 | 语义不变，不与 `deployVersion` 互相覆盖 |
| `database` / `containerWorkDir` / `serviceName` | 适配器在 `DEPLOY` 阶段末回写并落库 | 系统保留键（F-15） | 由主应用侧生成，`deployVersion` 及 `variables[].name` 不得占用；声明期与提交期校验必须把它们纳入（BR-07） |

#### 8.4.2 三态与键行为（MF-01 要求逐态定义「是否写键、写什么值」）

| 态 | 触发条件 | 向导表现 | 是否写 `deployVersion` | 写入值 | 扩展阶段 | BR-12 是否可能触发 |
| --- | --- | --- | --- | --- | --- | --- |
| **S1 无目录** | 该游戏无可用版本目录（无插件 / 未加载 / 目录为空 / 未通过 §8.1 校验），**且实例配置中不存在 `deployVersion` 键**（首次部署或从未选过非默认版本） | 不展示版本选择项 | **不写**（载荷与现状等价，不出现空值、不写 `"default"`） | — | 不进入 | 否（FR-02「等价于现状」仅在此态成立） |
| **S2 缺省默认** | 目录可用，用户未做选择或显式选择默认版本条目 | 展示选择项，停在默认项（或显式选默认） | **不写**；若实例配置中已存在该键（历史上选过非默认版本后又改回默认），**提交时删除该键**（FR-13） | — | 不进入 | 否 |
| **S3 显式非默认** | 目录可用且用户选择非默认版本条目，或实例配置已存在非默认 `deployVersion` 被重放（FR-13） | 展示选择项并停在所选项；目录不可用而键存在时**不改选也无法展示**，走 BR-12 | **写** | 所选条目的 `versionId` | 进入（按目录条目步骤集） | **是**（目录 / 声明不可用即拦截） |

**不变式（实现与验收共用判定）**：`configInfo.deployVersion` 存在 **⇔** 该实例的部署目标是非默认版本。BR-12 的触发条件、FR-02 的「等价于现状」边界、AC-19/AC-20 的断言对象全部由此式判定，不需要读取任何界面状态或日志文本。**该式的成立前提是「键不会被无关写路径静默删掉」，这一前提由 BR-16 守住（现状缺陷见 F-18 / AC-27）——否则不变式会在用户未做任何版本操作的情况下翻转。**

#### 8.4.3 撞键禁止清单（BR-07 校验对象）

`deployVersion` 在声明期与提交期都不得与以下键同名：① 该游戏 `variables[].name` 的任一取值（F-11 变量扁平铺顶部）；② 系统保留键 `database` / `containerWorkDir` / `serviceName`（F-15）；③ `gameVersion`（坏键，RISK-10）。

### 8.5 部署日志条目与「日志呈现契约」

沿用 `LogEntryVO{id,level,message,stage,time}` 与 `level ∈ INFO/WARN/ERROR/SUCCESS`。PRD 层约束（可观测要求）：

- 扩展阶段的每条日志 `stage` 值一致，且可与既有阶段值区分；
- 每步的「开始 / 成功或失败 / 耗时」三项对读者可见（FR-20）；
- 致命步骤失败行 `level = ERROR`，非致命步骤失败行 `level = WARN`。

**日志呈现契约（本文档不约定，交技术设计定）**：现有 `LogEntryVO` 既无步骤标识字段也无耗时字段（F-03），因此「同一步骤的三行如何归组」「耗时以何形式呈现」不能由 PRD 用 `message` 文本格式来钉。技术设计须给出并登记一份**日志呈现契约**，明确：① 步骤标识的承载位置（复用 `message` 内的固定前缀 / 扩展 VO 字段 / 其它，任选其一但须确定）；② 耗时的承载位置与单位；③ 三步行的归组规则。该契约是 **AC-03、AC-16、KPI-02 的核对前提**，未定稿或未登记时这三项一律记为「不可测」，禁止用人工阅读日志文本代替核对（评审 SG-05）。契约落点登记进 §14.2。

### 8.6 占位模板与验收资产的口径（OP-01 / OP-02 裁决后新增）

| 项 | 约定 |
| --- | --- |
| 占位模板的形态 | `plugin-dnf-tw` 模块内的一份版本目录模板，字段结构完整、符合 §8.1～§8.3 的全部校验规则；每个待填字段带**未填充标记**（标记写法与模板载体归技术设计，本文只约束其可观察结果）。模板本身必须显式标注「占位模板，不可上线」 |
| 未填充时的可观察结果 | 版本目录读取结果 = **空目录（0 条目）** → 命中 FR-02 / §8.4.2 **S1**：向导不展示版本选择项、提交载荷不写 `deployVersion`、不进入扩展阶段、部署与现状逐项一致（AC-02、AC-24） |
| 「填充即生效」的判定含义 | 人类 Owner 提供真实资料后，**只替换版本目录内容**即可让 S3 可达；若还需要改动框架代码、声明接口、数据库结构或主应用侧任何 `dnf_tw` 分支，即判 FR-23 未满足（验收不通过） |
| 验收夹具的内容边界 | 夹具 = 受控的补丁包 + 脚本正文 + 一个验收期间可达的受控来源，由 @Tester / @BackendDev 在验收阶段自行构造。本文档**不为夹具指定任何取值**，也不把夹具值算作 §8.2 的 dnf-tw 真实资料；本文档全文仍不含任何 `http(s)://` 字面量 |
| 三不得（BR-15 的操作性表述） | ① 不得用示例版号 / 示例 URL / 示例目标路径冒充可部署条目对外交付；② 不得把桩插件或夹具打进产品发布物、写入 `plugin-dnf-tw` 版本目录；③ 不得把桩插件 / 夹具的通过结果登记为 AC-05、KPI-01、KPI-03 的通过 |

| 时机 | 阶段 | 期望 `run_status` |
| --- | --- | --- |

| 启动并复检通过 | `START` → `COMPLETE` | `RUNNING`(1)，**首启即目标版本** |

## 10. 业务规则（BR-）

| 编号 | 规则 | 依据 |
| --- | --- | --- |
| BR-01 | 版本目录与扩展步骤的唯一承载方是**游戏插件声明**（ADR-0008 读时合并体系）；主应用 `core/` 不得内置任何游戏专属版本表或版本判断逻辑。dnf-tw 侧的承载方 = 本期新建的**最小 `plugin-dnf-tw` 模块**（FR-22、§5.1.1），过渡方案「先塞 `dnf_tw.yml` 基线」已被 G0 否决 | 决策 1、9；ADR-0002；OP-01（已裁决：是） |
| BR-02 | 「默认版本」= 不执行扩展步骤 + 沿用游戏 compose 模板既有镜像 tag；用户未做选择即等价默认版本，行为与现状一致 | 决策 9；F-09；AC-02 |
| BR-03 | 版本选择是实例部署配方的一部分：换版本走「改实例配置 → 重新部署」，不提供部署后就地改版本的旁路 | 决策 4；FR-13 |
| BR-04 | 步骤致命性默认 `true`；非致命只能由声明侧显式给出，主应用不得推断或覆盖 | 决策 5 |
| BR-05 | 补丁 `targetPath` 必须是相对实例安装目录 / 容器工作目录的安全相对路径；拒绝绝对路径与目录越界（`..`）；落位口径沿用 `PatchInstallService` | ADR-0006；F-05 |
| BR-06 | 步骤必须按幂等设计：在已达目标状态的实例上重复执行须成功且结果不变；幂等性由声明方（插件）负责，主应用不判断「是否已做过」 | 决策 4 |
| BR-07 | `deployVersion` 与 compose 变量键、系统保留键共存于同一扁平 `configInfo`，因此它必须是独立专用键，且**声明期与提交期都校验**它不与 §8.4.3 禁止清单中任何键同名——禁止清单显式包含 `variables[].name` 各键（F-11）、适配器回写的系统保留键 `database` / `containerWorkDir` / `serviceName`（F-15）、坏键 `gameVersion`（RISK-10）。校验不通过即拒绝提交并给出可辨识原因，不得静默覆盖任何一方 | F-11、F-15；AC-19 |
| BR-08 | 主应用按声明顺序执行，不重排、不同实例内并发；`PATCH` 与 `SCRIPT` 混排时同样遵循声明顺序 | 决策 2 |
| BR-09 | 补丁步骤沿用既有资源约束：全局并发 3、每宿主机互斥、自动重试 2 次（5s/20s 退避）、备份保留 5 份 | F-05 |
| BR-10 | 扩展阶段不改变既有阶段语义：`HEALTH_CHECK` / `START` 的判定标准、`UPDATE_STATUS` 置 `STOPPED`、`COMPLETE = 100%` 均不变 | 决策 8 |
| BR-11 | 未声明扩展步骤的游戏与插件，其部署阶段序列、进度百分比语义、状态转移与结果必须与改造前等价（回归基线） | 决策 2、8；G-04 |
| BR-12 | **（正式规则 — 经人类 G0 采纳，OP-06 关闭，2026-09-20）** **触发条件**（满足其一即触发；判定对象是 §8.4.2 不变式，可直接从实例配置读出，不依赖界面状态或日志文本）：① 本次部署**显式选择**了非默认版本；② 实例配置中**已存在**非默认 `deployVersion` 键（含 retry-deploy / 重部署的 FR-13 重放路径）。**触发后的行为**：只要该游戏版本目录不可用（插件未加载 / 声明接口异常 / 未通过 §8.1 校验 / 所选或已存的 `versionId` 不在目录中），部署必须失败、实例 `ERROR`、不启动、不交付，**不得静默按默认版本交付**，并在部署日志给出可辨识原因。**反向边界（不触发时）**：配置中不存在 `deployVersion` 键（S1 / S2）时，目录不可用只表现为「向导不展示选择项 + 按默认版本部署 + 一条 WARN/ERROR 日志行」，与现状等价（FR-02）。**为何只能在运行期拦**：本期不做向导期 / 环境校验期的版本可用性前置校验（N-09），扩展阶段入口是唯一判定点——这是 BR-12 存在的正当性依据。**与 dnf-tw 本期态的关系**：占位模板未填充时 dnf-tw 恒处 S1（§8.6），BR-12 对 dnf-tw 不触发，只对「已写入非默认键」的实例（含桩插件承载的实例）生效。依据：决策 5 对「选了指定版本却交付错版本是最糟的静默失败」的判定；本条**出处仍是决策 5 的推论**（Issue 正文与 ADR 未逐字写过，此说明保留作溯源），但**规则地位已由 G0 确认为正式**，不再保留「判定越界即删除 BR-12 / AC-20」的路径（OP-06 裁决） | 决策 5（推论）；OP-06 已采纳；N-09；FR-02/FR-13/§8.1 |
| BR-13 | 部署日志为内存态，本期不作为长期审计证据；验收证据须在部署过程内当次采集 | 决策 8；F-03 |
| BR-14 | **多步骤失败的回滚边界（显式声明，不留给实现方各自解释）**：① 只有**失败步骤自身**的补丁改动被回滚（FR-19，`PatchInstallService` 的备份粒度即此边界）；② **此前已成功步骤的改动一律保留**，不做反向补偿；③ **脚本步骤没有任何回滚**，其副作用（改文件、改数据库、装包等）在部署失败后原样留在实例上；④ 实例随后置 `ERROR`（FR-17）；⑤ 收敛方式只有一条：修正配方（声明侧由插件维护者修正该版本条目的补丁 / 脚本声明，即 FR-22 的插件声明；用户侧＝目录可用时改选版本）后重新部署，由 BR-06 幂等 + FR-13 重放把实例推回目标状态；「修正配方」不是界面上的撤销功能。本期不提供撤销已执行步骤、回退默认版本或事务式全量回滚的能力（N-08） | 决策 5；FR-19；BR-06；评审 SG-07；AC-21 |

## 11. 交付与验收边界

> G0 裁决（§13.4）把本期定性为「交付**框架 + 占位模板**，dnf-tw 真实版本资料缺口期」。这带来一个必须显式判定的问题：**哪些条目在缺口期仍然可验收、哪些不可验收**。不写清就会出两种事故——把框架类条目也一并记「不可测」（本期交付的框架无从验证），或反过来拿假资料 / 夹具的结果冒充真实版本验收通过（违反 OP-02 裁决）。本节给出唯一口径，§13.2 覆盖矩阵与 §13.1 的每条 AC 都以本节为判定基准。

### 11.1 缺口期承载方与「不可测」判定

| 承载方 | 覆盖条目 | 说明 |
| --- | --- | --- |
| **最小桩插件 + 验收夹具**（§5.1.1 验收资产，FR-24） | AC-01、AC-03、AC-04、AC-06、AC-07、AC-08、AC-09、AC-10、AC-11、AC-12、AC-13（仍受 RISK-05 前提约束）、AC-16、AC-18、AC-19、AC-20、AC-21、AC-22、AC-25、**AC-27** | 验证对象是**框架与步骤语义**（G-01 / G-03），与 dnf-tw 真实资料无关；结果**只计入框架类判定**，不得计入 AC-05 / KPI-01 / KPI-03（BR-15 ③） |
