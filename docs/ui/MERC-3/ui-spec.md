## 2. OP-05 定稿结论（交 Leader 统一回写 §6.1 / §6.2）

### ① 版本选择项落位：**部署向导步骤 2「选择游戏」右侧详情面板，紧随「部署方式」之后**

PRD §6.1 允许落在步骤 2 或步骤 3，本文取**步骤 2**，理由按权重排：

1. **目录的作用域由 gameCode + deployType 共同决定**（PRD §8.1 声明读取期、§6.1 步骤 2「切换部署方式需重取目录（F-08）」）。而部署方式这一控件只在步骤 2 存在。若版本项落在步骤 3，用户在步骤 2 改部署方式时，会**在视线之外**改掉步骤 3 已填的值——跨步隐式失效是最难被用户发现的交互缺陷。落在步骤 2，重取与回落都发生在同一屏、同一字段上，因与果相邻可见（原型 W4 / W6）。
2. **语义归属正确**：版本回答的是「部署哪一个版本」，与「部署方式」同类；步骤 3 是元数据 `configSchema` / `variables` 驱动的**零代码生成表单**（ADR-0002 范围隔离、ui-design-spec 3.3 步骤3）。把一个人工控件塞进自动生成表单区，会让该区块的渲染规则出现例外分支。
3. **满足 PRD 对步骤 3 的唯一硬约束**「提交前必须可见并可改」：控件在步骤 2，「可改」由既有「上一步」回溯满足（该步内容全程 `v-show`、不卸载，改值不丢失）。

配套结论：

- **区块形态**：沿用步骤 2 既有 `.detail-section`（`section-title` 13px/650 + 下边框 + 16px 下边距），控件为 `el-select`，宽度沿用既有 `el-select` 的 `width: 300px` 惯例（`deploy.vue:1425`）。不新增卡片、不新增步骤、不改 `steps` 数组。
- **默认项文案恒为「默认版本」**四字，**不显示镜像 tag 字面量**——BR-02 定义默认版本 = 沿用游戏模板内既有 tag，本就没有独立 **`imageTag`** 可展示；显示 tag 反而会把 F-09 的内部事实暴露成用户可选信息。**「没有 `imageTag`」不等于「没有 `versionId`」**：该条目的 `versionId` 副标仍照常渲染（§6.1「默认项副标取值」支①），只有当目录里**不存在** `default = true` 条目时，首位「默认版本」才没有副标（支②，原型 W3b / W8c）。该条目即使声明了 `displayName` 也**有意不采用**（§6.1 已明写）。
- **选项文本 = `displayName`（缺省回退 `versionId`），且 `versionId` 恒以 mono 副标同时呈现**（Leader 裁定 1，口径与 AC-01 的机械核对对象见 §6.1）。
- **单值目录不隐藏控件**（PRD §12「是否隐藏单值控件归 @Designer」）：控件是否出现只由**一个**谓词「目录是否可用」决定，条目数只决定选项多寡。若改成按条目数决定，插件维护者增删条目会让控件反复出现/消失，用户也失去「版本在这里改」的稳定落点。单值态等价 S2（不写键、不进扩展阶段），与 §12 系统表现列一致。原型 W5 现以下拉**展开态**直接呈现「只有一个可选值」。**同一条「只看一个谓词」的结论在 v0.5 覆盖到 G2**：载荷里的 `versionId` 不在目录条目中时控件**仍渲染**——该谓词只决定当前值怎么显示，不决定控件出没出现（§4.1 G2 / §5 / §7 X-11，实物屏 **W9b**）。

### ② 扩展阶段用户可见名称：**「部署扩展」**

| 候选 | 判定 | 理由 |
| --- | --- | --- |
| **部署扩展** | **采纳** | 与 `glossary.md` 的领域术语「部署扩展阶段（Deploy Extension Stage）」「部署扩展步骤（Deploy Extension Step）」逐字一致；对用户而言「部署」是已知语境词，「扩展」表达"在部署之内的额外处理"而不承诺具体手段。文档、日志、界面同一词，运维讨论时可直接引用界面文字（该词是核对 AC-16 / KPI-02 的对象，词面分裂会直接产生歧义）。 |
| 版本定制 / 版本处理 | 否 | 只对 dnf-tw 的首个用例成立。框架必须能承载与版本无关的扩展步骤（决策 1、G-01），用「版本」命名会对那些步骤说谎。 |
| 补丁与脚本 | 否 | 暴露实现种类；将来新增步骤类型即名不副实；且种类词已在**步骤行**呈现（§6.2），阶段名再重复一层是噪声。 |

配套：两类步骤的用户可见名称定为 **「补丁替换」（PATCH）** / **「脚本执行」（SCRIPT）**；步骤副属性用平实措辞 **「失败即终止」/「失败可继续」** 表达 `fatal`，界面不出现 "fatal" 字样（§8 的字段名是声明侧语言，不是用户语言）。

### ③ 失败提示文案：见 §6 文案矩阵

三项要求全部落定：(a) BR-12 两类可辨识原因的词面已分别定稿并保证「只靠两处长短不同的短语即可区分」；(b) 三类目录异常态（未填充 / 不合法 / 不可用且键既存）的措辞互斥，不可互相冒充；(c) 全部措辞不暗示界面上不存在的操作（对齐 PRD v0.4 对 §12 的收口）。

## 5. 可见性判定规则（设计不变式）

把 §4.1 的十二条状态（A–J + F2 + G2）收成一个可实现、可核对的三值规则，避免实现侧各自解释：

```
P1  控件渲染  ⇔  目录可用（读取成功 且 条目数 ≥ 1）
P2  摘要行渲染 ⇔  P1  ∨  提交载荷含 deployVersion
P3  扩展阶段呈现（阶段带 / 步骤点 / statusText）
       ⇔  本次部署真的进入了扩展阶段（未进入则一切如旧）
```

**P1 的判据到此为止，不再加条件**（v0.5，MF-7）：**不**把「载荷里的 `versionId` 是否在条目中」并进 P1。该谓词只决定**当前值怎么显示**（G2），不决定**控件出不出现**——这是 §2-①「控件出现与否只由『目录是否可用』一个谓词决定」的延续。若把它并进 P1，用户恰恰在**最需要改选**的形态下失去了改选入口（控件一消失，异常值就只能靠提交后在部署日志里发现），而 §2-① 立这条规则的理由（控件不因目录内容增删而忽现忽隐）在该态下同样成立。

摘要行取值：

| 载荷 | 摘要显示 | 原型屏 | 依据 |
| --- | --- | --- | --- |
| 无 `deployVersion`，P1 真 · 目录**存在** `default = true` 条目（支①） | 「默认版本」+ **该条目的 `versionId`** mono 副标 | **W8b** | FR-04；§6.1「默认项副标取值」支① |
| 无 `deployVersion`，P1 真 · 目录**无** `default = true` 条目（支②） | 「默认版本」四字、**不渲染副标**——该「默认版本」不是目录条目，没有 `versionId` 可取；**不得**为它编一个目录里不存在的字符串 | **W8c** | §8.1 校验「`default = true` 至多一条」⇒ 0 条合法；§6.1 支② |

| **有 `deployVersion`，P1 真 · 该值不在条目中（G2）**（v0.5，MF-7） | **`versionId` + 「沿用实例配置」标识**（与 W9 同款：该条目的 `displayName` 与目录不可用时一样**无从解析**，只能报出载荷里真实存在的那个值）；**另加一句「不在当前可选版本中」**，并说明「改选下列任一条目即可覆盖，不改选直接提交时该键原样携带、由扩展阶段入口按 §6.3 分支 ② 拦截」。**步骤 2 的控件仍在且可改选**（区别于 W9），故该态**不是**「不可改选」的呈现 | **W9b** | FR-13 / §8.4.2 / **BR-12**（PRD 明列该触发条件）/ AC-20 (b) |

| 无 `deployVersion`，P1 假 | **不渲染该行** | W7 | 见下（§10-A 已裁定） |

**P2 的第三条（S1 不显示「默认版本」）已由 Leader 裁定采纳**：口径为给 FR-04 加限定「（目录可用时）」、§6.1 步骤 5 行改为「摘要须显示所选版本（目录可用时；无可用目录时不渲染该行）」，随 PRD v0.6 一次回写。理由：FR-04「未选择时显示默认版本」以「用户本可以选择」为前提；S1 下没有任何可选项，多出一行会让 AC-24 ④「与改造前逐项一致」不再成立。

**P2 取值的健壮性要求**：摘要行的有无与内容一律**由提交载荷推导，不由目录状态推导**。这样在「目录读取失败但键既存」的 H 态下，界面仍然诚实显示版本要求，而不是伪装成一次默认版本部署——那正是 BR-12 要杜绝的结果在界面上的翻版。**同一条推导在 G2（v0.5）下给出它唯一的诚实呈现**：载荷里有一个目录给不出的 `versionId`，摘要与控件就报那个字符串本身，既不回落「默认版本」（那是伪造取值），也不因「找不到条目」而省掉该行（那是让异常要求消失）。

### 6.2 阶段与步骤行

`〈…〉` 为字段槽位；`·` 前为固定词面。**行内步骤标识与耗时最终落在哪个字段由 §8.5 契约定，本节定的是渲染出来的文本。**

| 场景 | 词面 | level |
| --- | --- | --- |
| 进入阶段 | `进入部署扩展阶段` | INFO |
| 停实例前置 | `正在停止实例，确保扩展步骤在实例未运行时执行` | INFO |
| 停实例完成 | `实例已停止` | SUCCESS |
| 停实例失败 | `实例停止失败：〈原因〉 —— 扩展步骤不得在实例仍运行时执行，部署终止` | ERROR |
| 步骤开始 | `步骤 〈序号〉/〈总数〉 〈步骤标签〉 · 〈种类〉 开始` | INFO |
| 步骤成功 | `步骤 〈序号〉/〈总数〉 〈步骤标签〉 · 〈种类〉 · 成功 · 耗时 〈时长〉` | SUCCESS |
| 步骤失败·致命 | `步骤 〈序号〉/〈总数〉 〈步骤标签〉 · 〈种类〉 · 失败 · 耗时 〈时长〉 · 原因：〈原因〉` | ERROR |
| 步骤失败·非致命 | 同上加「失败（非致命）」 | WARN |
| 致命终止 | `致命步骤失败，部署终止：不再执行后续步骤，实例不启动、不交付，状态置为异常` | ERROR |
| 非致命继续 | `该步骤声明为非致命，继续执行后续步骤` | INFO |
| **阶段收尾 · 成功支**（v0.5，⑧a） | `部署扩展阶段收尾 · 容器已恢复到运行态 · 成功 · 耗时 〈时长〉` | SUCCESS |
| **阶段收尾 · 失败支**（v0.5，⑧a） | `部署扩展阶段收尾 · 容器未能恢复到运行态 · 失败 · 原因：〈原因〉`，**行后不接阶段完成行、不接交棒行** | ERROR |
| 阶段完成 | `部署扩展阶段完成 · 共 〈总数〉 步 · 总耗时 〈时长〉` | SUCCESS |

（向导侧的步数徽标 / 选项行右侧步数及其 0 值档不在本表——它们是控件词面不是日志行，册在 §6.1「↳ 步数徽标与选项行右侧步数」。）

规则：

- **扩展阶段内的行序列（v0.5 按 ⑧b/⑧c 定死，机械锚点）**：
  `阶段带 → 进入部署扩展阶段 → 停实例两行 → 步骤行（逐步三行一组）→ **收尾行** → 阶段完成行 → 交棒行`。
  四条要点：
  ① **收尾行只在「全部步骤已判定完成」时产生**（成功支或失败支二选一）；未判完全部步骤的三种情形**不产收尾行**——致命失败中途终止（LC / LH / LI 的失败行之后即「致命步骤失败，部署终止」）、停实例失败（E1）、扩展阶段入口的 BR-12 拦截（LE / LF，未执行任何步骤）。
  ② **失败支终止于此**：其后不得出现阶段完成行、交棒行，也不得出现 `[HEALTH_CHECK]` 行（技术设计 §14.13.3「失败处置」：部署判失败、实例 `ERROR`、不进入 `HEALTH_CHECK`）。
  ③ 收尾行与相邻两行的先后**同为核对对象**：**必须在最后一步的终态行之后、阶段完成行之前**（X-07）。
  ④ **`〈总耗时〉` 含收尾那一段**：阶段完成行的 `〈总耗时〉` = 进入行到完成行的整段，收尾行的 `〈时长〉` 只计收尾这一段（技术设计 §14.12 / §14.6 `elapsedMs` 行的分工）。两条行都是**阶段级行**、都不进步骤归组主键，因此都不进 KPI-02 的分母（该口径归技术设计 V-08，UI 侧只固定词面与顺序）。
  这条序列就是 AC-03 / AC-16 的机械锚点，30 屏无一例外，速查帧（LH / LI）与新增的 LK 也照此画（§7 X-07）。
- **`label` 缺省时的渲染回退**：PRD §8.2 / §8.3 给声明侧的缺省值是「序号 + `PATCH` / `SCRIPT`」，那是声明侧语言，界面**不照抄**（`patch` 在 §6.1 是禁用替代词，且会与同行的种类徽标重复）。渲染侧一律回退为 **「补丁替换 〈序号〉」/「脚本执行 〈序号〉」**——即缺 `label` 时用「种类 + 序号」，绝不让 `PATCH` / `SCRIPT` 字面量出现在日志行或步骤预览里。
- **耗时格式沿用既有实现** `formattedElapsedTime`（`DeployProgress.vue:72-85`）：`N秒` / `N分N秒` / `N小时N分`。**不引入裸 ms**。这与该对话框顶部「已用时」同源，用户不需要学第二套读法。
- **`〈总数〉` 若执行期不可得**，退化为 `步骤 〈序号〉 〈步骤标签〉 · …`。总数只在阶段入口计算步骤集时可得（FR-05 / FR-12），不得为此新增接口。
- **原因段一律以「原因：」引导**并置于行尾，便于 KPI-03 归因时机械截取。
- 三行同属一步的**归组判读**以 §8.5 契约为准；本设计的阶段带提供阶段级归组，步骤级归组由契约的 `〈序号〉/〈总数〉` + 同一 `〈步骤标签〉` 词面支撑。

### 6.3 失败与拦截（含 BR-12 两类可辨识原因）

**AC-20 要求「区分是本次所选还是配置既存键」。两类文案只在两处长得不同，且这两处各自唯一：**

| 分支 | 首行（指名原因） | 追加行 |
| --- | --- | --- |
| ① 本次显式选择 | `部署终止：本次所选版本 〈versionId〉 不可用 —— 该游戏的版本目录当前不可读取或未通过声明校验` | `实例未启动、未交付，状态置为异常；该版本要求不会被静默改为默认版本` |
| ② 配置既存键 | `部署终止：实例配置要求的版本 〈versionId〉 不可用 —— 该版本要求由既往部署写入实例配置，本次未改选；而该游戏的版本目录当前不可读取或未通过声明校验` | 上一行 + `恢复路径：先恢复该游戏的版本目录（重新启用插件，或由插件维护者修复声明）后重新部署；目录恢复后如不再需要该版本，请在「选择游戏」步骤改选「默认版本」再部署（目录未恢复时该选项不存在）` |

区分锚点：**「本次所选」vs「实例配置要求的…由既往部署写入」**，以及**恢复路径行只在 ② 出现**。核对脚本按这两个锚点即可机械判定，不需读界面状态。

**这两行为什么指名 `versionId` 而不是 `displayName`**：BR-12 触发的前提正是「目录不可读取 / 未过校验」，此时 `displayName` 无从解析——日志只能报出**载荷里真实存在的那个值**（`deployVersion` = 某条目的 `versionId`）。这与 W9 摘要同口径：界面在目录可用时用展示名，在目录不可用时一律回到 `versionId`，两处报的是同一个字符串，用户才可能对得上。

**② 的措辞红线**（PRD v0.4 对 §12 的收口）：

- 禁止「在向导改选默认版本即可解锁」这类把解锁路径写成界面上不存在的操作的表述——恢复顺序必须先是「恢复版本目录」，改选默认版本是其**之后**的分支，并用括号点明「目录未恢复时该选项不存在」。
- 禁止任何「一键清除版本要求 / 回退默认版本」类控件与措辞（N-08、§12 明写本期不提供）。

| X-08 | 「扩展」步骤点插入 | 在「配置」与「启动」之间插入；**五个既有点的 completed / active 判定结果在插入瞬间不得变化**（否则用户会看到进度倒退） |
| X-09 | 点「重试」 | 沿用既有行为（清空日志、重新轮询）。retry-deploy 先 `uninstall` 的后果归 §14.2 / RISK-09，非 UI 层可判定，本文不预设 |
| **X-10** | **选项排序（v0.5，S-16 提进规则层）** | 「默认版本」恒为下拉**第一项**：目录里 `default = true` 的条目若不在声明序首位，**渲染时上提**；其余条目保持声明序、不做字典序重排；无该条目时首位是合成项（§6.1 支②）。**句二的判据依赖本条**，故它必须是规则正文，不能只活在原型的标注卡里。详见 §6.1「↳ 选项排序」 |
| **X-11** | **G2：目录可用但载荷版本不在条目中（v0.5，MF-7）** | 三条硬规则：① **控件照常渲染、可改选**——出现与否只看「目录是否可用」（§2-① / §5 P1），该态下用户恰恰需要改选回目录内条目，隐藏控件等于剥夺改正能力；② **不得回落为「默认版本」，不得清除或改写已有的 `deployVersion` 键**——**后果写死**：一旦回落，「回落 + 提交时删键（§8.4.2 S2）」就连同 BR-12 的触发条件一起抹掉，部署会**静默按默认版本交付**，用户点「下一步」时看不出任何异常，而 D-04 / W9 整套「诚实呈现」设计要防的正是这个结果，只是换了一个入口进来；③ **未改选直接提交时，载荷必须原样携带该键**，由扩展阶段入口按 **BR-12 分支 ②** 拦截（§6.3 措辞）。**边界**：用户随后改选目录内任一条目属正常改选，键随之被该条目的 `versionId` 覆盖，不在 ② 的禁止范围内。该态**不经步骤 4 校验**（N-09：目录可用性不做前置探测），所以界面是它唯一的可见化机会——错过这一次就只能到部署日志里才知道 |

3. **动效**：步骤点的 `transition: all .3s` 与 loading 旋转属非信息性动效；信息变化同时以文字呈现，满足 `prefers-reduced-motion` 降级。
4. **键盘与语义**：`el-select` 沿用 Element Plus 原生键盘操作（↑↓ / Enter / Esc）；区块标题与控件建立 `aria-labelledby` 关联。
   **日志播报机制定稿（v0.4，S-12）**：`role="log"` 的语义本身就是逐条增量播报，与「不得逐行播报」**不能同时按字面落地**，因此改为**分工并用**而非在同一元素上叠加两个属性——
   - **滚动容器 `.logs-container`**：保留 `role="log"`（日志语义与滚动区可发现性），但 **`aria-live="off"`** ⇒ **不逐行播报**。2 秒轮询每轮可能一次追加多条，逐行播报会把对话框变成刷屏，读屏用户反而什么都听不清。
   - **另设视觉隐藏区**（原型内类名 `.sr-only`，实现侧同名或等价的 `clip-path` 方案）：**三个属性同时显式写出**——`role="status"` + `aria-live="polite"` + **`aria-atomic="false"`**。第三项**必须写出来、不得依赖隐含值**：`role="status"` 的隐含语义除 `aria-live="polite"` 外**还包含 `aria-atomic="true"`**，即「该区域发生任何变更 ⇒ 播报**整个区域**的内容」；本区承载的是**只增不减的累积队列**，沿用隐含值的结果是每来一条新事件或新 ERROR 行，读屏都把整条队列从头重播一遍、长度逐轮变长——那正是下一条红线要禁的事（从「逐行播报」退化成**更差的「累积重播」**）。**（v0.5，MF-6）**
   - **写入方式 = 增量 append 单个节点**：每轮只向该区域**追加一个新的直接子节点**，**不清空、不整体重建**该区域的子节点集。**这两句必须同时成立**：只写 `aria-atomic="false"` 而实现按数组整体重渲染（`innerHTML` 整刷 / 列表全量 diff），部分读屏实现仍会整段重播；只写增量 append 而漏 `aria-atomic="false"`，则 `status` 的隐含 `true` 让每次追加都播整段。**（v0.5，MF-6）**
   - **判据的口径是「播报行为」，不是「内容」**（v0.5 起改写，MF-6；**v0.6 按 S-18 把量词改准**）：**每次变更只播本轮新增的那些条——既有任何一条都不重播**。本条**不要求「恰一条」**：本节开头「滚动容器 / 另设视觉隐藏区」那段已写明「2 秒轮询每轮可能一次追加多条」，一轮追加 3 条是正确实现，旧写法（「只播新增的那一条」）会把它判成 FAIL。静态产物上的机械判据三条，缺一不可：
     ① 该区域的开始标签**同时**带 `role="status"` / `aria-live="polite"` / `aria-atomic="false"` 三项——缺第三项即按本条判 FAIL，**不接受**「库里 `status` 默认就是这个行为」的辩解（默认值恰是 `true`）；
     ② **一条一个节点**：每个合格行各占一个直接子节点，不得把多条拼进同一节点、不得写成整段文本——这是「变化的部分 = 本轮新增的那些条」的结构前提；
     ③ **子节点文本集合恰好等于**「① 阶段级三条事件（`进入部署扩展阶段` / `部署扩展阶段完成 · …` / `部署扩展阶段结束…`）**+ ② 全部 ERROR 行」这一集合——既不少也不多。**这就是「非全文镜像」的机械形式**：做成镜像会让同一集合等于「该屏全部日志行」，两者只在 LB / E3（队列为空）与 E2（唯一一行本身就是 ERROR）重合，而这三屏都没有可镜像的多余行。逐屏实测（v0.5 对本版实物全量 render 后的**节点数 / 非带日志行数**，15 屏全列，供定点复判直核）：**LA 3/16 · LJ 3/16 · LD 3/16 · LC 3/12 · LH 4/12 · LI 5/10 · LK 2/12 · LE 3/5 · LF 3/6 · E1 3/4 · E2 1/1 · E4 1/4 · LB 0/4 · LG 0/4 · E3 0/0**。。
     实现侧另加一条行为核对：变更前后 diff 该区域的子节点，**新增数 = 本轮新增的合格行数（≥ 1，不要求恰为 1），且既有节点的文本与顺序全部保留**（v0.6，S-18）（原型内 `.sr-only` 由静态终态生成，本条在原型侧核 ①②③）。
   - **队列只承载两类变化点**：① **阶段级事件三条**（`进入部署扩展阶段` / `部署扩展阶段完成 · 共 〈总数〉 步 · 总耗时 〈时长〉` / `部署扩展阶段结束，进入健康检查与启动`）；② **ERROR 行全文**（含「原因：」段，AC-08 / AC-20 的归因对象）。除此以外的行（含 INFO / WARN 与普通成功行）一律不进队列。
   - **两条红线**：不得把该隐藏区做成日志全文的镜像（**判据按上一行的「播报行为」读**：内容镜像会退化成逐行播报，累积重播同样不成立）；不得让 INFO / WARN 行进播报队列（非致命失败由 §6.2 的 WARN 行**可见**，播报队列保持 ERROR-only，避免同一事实被念两遍——判据见 §4.2 O 行与 AC-10）。
   - 播报文本 = 界面可见文本（§6.2 词面），**不另设一套读法**；阶段带自身不播报，由紧随的进入行承担。
   - **收尾行两支在队列里的归属（v0.5，⑧a）**：**失败支进队列**——它是 `ERROR` 行，按第 ② 类原样入队；**成功支不进队列**——它是阶段级 `SUCCESS` 行，但紧随其后的「阶段完成行」已在第 ① 类里播报同一阶段的收束，连播两条会把 §9.4 的「避免同一事实被念两遍」口径稀释，而成功收尾不是需要用户行动的信息。判据：该阶段的**成功**由阶段完成行播报，该阶段的**失败**由收尾失败行播报，两者在任一屏不同时出现。
   - **原型已实画该分工**（v0.4 落地、v0.5 补齐第三属性）：15 个日志屏全部带 `role="log" aria-live="off"` 的容器，与一个 `.sr-only` `polite` **+ `aria-atomic="false"`** 区；逐屏队列内容 = 该屏的阶段级三条事件 + 全部 ERROR 行（LB / E3 未进入扩展阶段 ⇒ 队列为空；**LK（收尾失败支）只播该条 ERROR 收尾行、不播交棒行**——收尾失败即终止，该阶段没有交棒行，见 §6.2 规则 1）；LD 只播报阶段事件、其 WARN 行不播。
5. **不依赖记忆**：致命性、既存键来源、恢复路径都以文字写在界面内，不要求用户记住上文（§6.1 的用词理由）。
