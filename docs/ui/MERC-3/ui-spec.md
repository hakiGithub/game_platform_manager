## 2. OP-05 定稿结论（交 Leader 统一回写 §6.1 / §6.2）

### ① 版本选择项落位：**部署向导步骤 2「选择游戏」右侧详情面板，紧随「部署方式」之后**

PRD §6.1 允许落在步骤 2 或步骤 3，本文取**步骤 2**，理由按权重排：

1. **目录的作用域由 gameCode + deployType 共同决定**（PRD §8.1 声明读取期、§6.1 步骤 2「切换部署方式需重取目录（F-08）」）。而部署方式这一控件只在步骤 2 存在。若版本项落在步骤 3，用户在步骤 2 改部署方式时，会**在视线之外**改掉步骤 3 已填的值——跨步隐式失效是最难被用户发现的交互缺陷。落在步骤 2，重取与回落都发生在同一屏、同一字段上，因与果相邻可见（原型 W4 / W6）。
2. **语义归属正确**：版本回答的是「部署哪一个版本」，与「部署方式」同类；步骤 3 是元数据 `configSchema` / `variables` 驱动的**零代码生成表单**（ADR-0002 范围隔离、ui-design-spec 3.3 步骤3）。把一个人工控件塞进自动生成表单区，会让该区块的渲染规则出现例外分支。
3. **满足 PRD 对步骤 3 的唯一硬约束**「提交前必须可见并可改」：控件在步骤 2，「可改」由既有「上一步」回溯满足（该步内容全程 `v-show`、不卸载，改值不丢失）。

配套结论：

- **区块形态**：沿用步骤 2 既有 `.detail-section`（`section-title` 13px/650 + 下边框 + 16px 下边距），控件为 `el-select`，宽度沿用既有 `el-select` 的 `width: 300px` 惯例（`deploy.vue:1425`）。不新增卡片、不新增步骤、不改 `steps` 数组。
- **默认项文案恒为「默认版本」**四字，**不显示镜像 tag 字面量**——BR-02 定义默认版本 = 沿用游戏模板内既有 tag，本就没有独立版号可展示；显示 tag 反而会把 F-09 的内部事实暴露成用户可选信息。
- **单值目录不隐藏控件**（PRD §12「是否隐藏单值控件归 @Designer」）：控件是否出现只由**一个**谓词「目录是否可用」决定，条目数只决定选项多寡。若改成按条目数决定，插件维护者增删条目会让控件反复出现/消失，用户也失去「版本在这里改」的稳定落点。单值态等价 S2（不写键、不进扩展阶段），与 §12 系统表现列一致。

### ② 扩展阶段用户可见名称：**「部署扩展」**

| 候选 | 判定 | 理由 |
| --- | --- | --- |
| **部署扩展** | **采纳** | 与 `glossary.md` 的领域术语「部署扩展阶段（Deploy Extension Stage）」「部署扩展步骤（Deploy Extension Step）」逐字一致；对用户而言「部署」是已知语境词，「扩展」表达"在部署之内的额外处理"而不承诺具体手段。文档、日志、界面同一词，运维讨论时可直接引用界面文字（该词是核对 AC-16 / KPI-02 的对象，词面分裂会直接产生歧义）。 |
| 版本定制 / 版本处理 | 否 | 只对 dnf-tw 的首个用例成立。框架必须能承载与版本无关的扩展步骤（决策 1、G-01），用「版本」命名会对那些步骤说谎。 |
| 补丁与脚本 | 否 | 暴露实现种类；将来新增步骤类型即名不副实；且种类词已在**步骤行**呈现（§6.2），阶段名再重复一层是噪声。 |

配套：两类步骤的用户可见名称定为 **「补丁替换」（PATCH）** / **「脚本执行」（SCRIPT）**；步骤副属性用平实措辞 **「失败即终止」/「失败可继续」** 表达 `fatal`，界面不出现 "fatal" 字样（§8 的字段名是声明侧语言，不是用户语言）。

### ③ 失败提示文案：见 §6 文案矩阵

三项要求全部落定：(a) BR-12 两类可辨识原因的词面已分别定稿并保证「只靠两处长短不同的短语即可区分」；(b) 三类目录异常态（未填充 / 不合法 / 不可用且键既存）的措辞互斥，不可互相冒充；(c) 全部措辞不暗示界面上不存在的操作（对齐 PRD v0.4 对 §12 的收口）。

## 5. 可见性判定规则（设计不变式）

把 §4 的十条状态收成一个可实现、可核对的三值规则，避免实现侧各自解释：

```
P1  控件渲染  ⇔  目录可用（读取成功 且 条目数 ≥ 1）
P2  摘要行渲染 ⇔  P1  ∨  提交载荷含 deployVersion
P3  扩展阶段呈现（阶段带 / 步骤点 / statusText）
       ⇔  本次部署真的进入了扩展阶段（未进入则一切如旧）
```

摘要行取值：

| 载荷 | 摘要显示 | 依据 |
| --- | --- | --- |
| 无 `deployVersion`，P1 真 | 「默认版本」 | FR-04 |
| 有 `deployVersion` | 该 `versionId` + 「沿用实例配置」或「本次选择」标识 | FR-13 / §8.4.2 S3 / AC-20 |
| 无 `deployVersion`，P1 假 | **不渲染该行** | 见下 |

**P2 的第三条（S1 不显示「默认版本」）是对 FR-04 的一处解读，与 FR-04 字面冲突，已交 Leader 定夺**（§10-A）。理由：FR-04「未选择时显示默认版本」以「用户本可以选择」为前提；S1 下没有任何可选项，多出一行会让 AC-24 ④「与改造前逐项一致」不再成立。

**P2 取值的健壮性要求**：摘要行的有无与内容一律**由提交载荷推导，不由目录状态推导**。这样在「目录读取失败但键既存」的 H 态下，界面仍然诚实显示版本要求，而不是伪装成一次默认版本部署——那正是 BR-12 要杜绝的结果在界面上的翻版。

| 控件标签 | 目标版本 | 游戏版本（与坏键 `gameVersion` 撞名，RISK-10）、版本目录（那是声明侧概念，不是用户选项） |

| 步骤种类 PATCH | 补丁替换 | 打补丁、patch |
| 步骤种类 SCRIPT | 脚本执行 | 跑脚本、shell |
| `fatal = true` | 失败即终止 | 致命 |

### 6.2 阶段与步骤行

`〈…〉` 为字段槽位；`·` 前为固定词面。**行内步骤标识与耗时最终落在哪个字段由 §8.5 契约定，本节定的是渲染出来的文本。**

| 场景 | 词面 | level |
| --- | --- | --- |
| 进入阶段 | `进入部署扩展阶段` | INFO |
| 停实例前置 | `正在停止实例，确保扩展步骤在实例未运行时执行` | INFO |
| 停实例完成 | `实例已停止` | SUCCESS |
| 停实例失败 | `实例停止失败：〈原因〉 —— 扩展步骤不得在实例仍运行时执行，部署终止` | ERROR |
| 步骤开始 | `步骤 〈序号〉/〈总数〉 〈步骤标签〉 · 〈种类〉 开始` | INFO |
| 步骤成功 | `步骤 〈序号〉/〈总数〉 〈步骤标签〉 · 〈种类〉 · 成功 · 耗时 〈时长〉` | SUCCESS |
| 步骤失败·致命 | `步骤 〈序号〉/〈总数〉 〈步骤标签〉 · 〈种类〉 · 失败 · 耗时 〈时长〉 · 原因：〈原因〉` | ERROR |

| 非致命继续 | `该步骤声明为非致命，继续执行后续步骤` | INFO |

规则：

- **耗时格式沿用既有实现** `formattedElapsedTime`（`DeployProgress.vue:72-85`）：`N秒` / `N分N秒` / `N小时N分`。**不引入裸 ms**。这与该对话框顶部「已用时」同源，用户不需要学第二套读法。
- **`〈总数〉` 若执行期不可得**，退化为 `步骤 〈序号〉 〈步骤标签〉 · …`。总数只在阶段入口计算步骤集时可得（FR-05 / FR-12），不得为此新增接口。
- **原因段一律以「原因：」引导**并置于行尾，便于 KPI-03 归因时机械截取。
- 三行同属一步的**归组判读**以 §8.5 契约为准；本设计的阶段带提供阶段级归组，步骤级归组由契约的 `〈序号〉/〈总数〉` + 同一 `〈步骤标签〉` 词面支撑。

### 6.3 失败与拦截（含 BR-12 两类可辨识原因）

**AC-20 要求「区分是本次所选还是配置既存键」。两类文案只在两处长得不同，且这两处各自唯一：**

| 分支 | 首行（指名原因） | 追加行 |
| --- | --- | --- |
| ① 本次显式选择 | `部署终止：本次所选版本 〈versionId〉 不可用 —— 该游戏的版本目录当前不可读取或未通过声明校验` | `实例未启动、未交付，状态置为异常；该版本要求不会被静默改为默认版本` |
| ② 配置既存键 | `部署终止：实例配置要求的版本 〈versionId〉 不可用 —— 该版本要求由既往部署写入实例配置，本次未改选；而该游戏的版本目录当前不可读取或未通过声明校验` | 上一行 + `恢复路径：先恢复该游戏的版本目录（重新启用插件，或由插件维护者修复声明）后重新部署；目录恢复后如不再需要该版本，请在「选择游戏」步骤改选「默认版本」再部署（目录未恢复时该选项不存在）` |

区分锚点：**「本次所选」vs「实例配置要求的…由既往部署写入」**，以及**恢复路径行只在 ② 出现**。核对脚本按这两个锚点即可机械判定，不需读界面状态。

**② 的措辞红线**（PRD v0.4 对 §12 的收口）：

- 禁止「在向导改选默认版本即可解锁」这类把解锁路径写成界面上不存在的操作的表述——恢复顺序必须先是「恢复版本目录」，改选默认版本是其**之后**的分支，并用括号点明「目录未恢复时该选项不存在」。
- 禁止任何「一键清除版本要求 / 回退默认版本」类控件与措辞（N-08、§12 明写本期不提供）。

**其他异常态文案：**

| 场景 | 词面 | level |
| --- | --- | --- |
| 目录不合法 + 无键（S1，不拦截） | `提示：该游戏版本目录的声明不合法（〈校验失败要点〉），已按默认版本部署，未执行部署扩展步骤` | WARN |
| 补丁来源不可达 | `原因：补丁包来源不可达〈补丁来源〉` | 按致命性 |
| 摘要不符 | `原因：补丁包摘要与声明不符（期望 〈sha256〉，实际 〈sha256〉）` | 按致命性 |
| 脚本非零退出 | `原因：脚本退出码 〈exitCode〉（非 0 即判失败）` | 按致命性 |
| 脚本超时 | `原因：脚本执行超过 〈timeoutMs〉 未返回，判失败` | 按致命性 |
| SSH 不可达 | `原因：宿主机 〈主机名〉 SSH 通道不可用 —— 〈原因〉` | 按致命性 |
| 回滚成功 | `目标路径已回滚到本次改动前状态（备份：〈备份标识〉）` | SUCCESS |
| 回滚失败 | `回滚失败：〈原因〉（备份 〈备份标识〉）。目标路径未恢复到本次改动前状态` + `平台侧不提供恢复入口，需在宿主机上手工处理后重新部署` | ERROR |
| 保留边界 | `此前已成功步骤的改动与脚本副作用一律保留，本期不提供撤销` | WARN |
| 对话框错误条（`data.error`） | `部署扩展阶段的致命步骤失败：〈步骤标签〉 · 〈种类〉。实例状态已置为异常，未启动。` | — |

**归因一致性**：KPI-03 要求每次失败归入「实现缺陷 / 排除项①声明不可用 / 排除项②资料缺失 / 排除项③外部资源」四类之一。上表中「BR-12 拦截」两行、「目录不合法」一行、「来源不可达 / 摘要不符」两行分别对应 ①、①、③——词面已确保读者能从文案直接归类，不需回查文档。

## 9. 无障碍与响应式

**无障碍**

1. **三重标识**：状态以「颜色 + 图标 + 文字」表达（ui-design-spec 2.2.3）。阶段带除色以外还带**文字**「部署扩展」，ERROR 行除红色外还有 `[ERROR]` 与 `CircleClose` 图标——阶段判读不依赖颜色辨别。
2. **对比度**（对页面底 `--platform-surface-0 #0b1722` 实测 WCAG 相对亮度比）：`--platform-amber` **10.1:1**、`--platform-green` **9.1:1**、`--platform-cyan` **7.8:1**、`--platform-red` **5.8:1**、`--platform-text-secondary` **6.5:1**、`-regular` **11.3:1**、`-primary` **15.5:1** —— 本期所有状态与正文文字均在 AA（4.5:1）以上。
   **一条本期要遵守的约束**：`--platform-text-muted #68788a` 仅 **4.0:1**，未达正文 AA。因此目标版本区块、步骤预览、摘要行、阶段带等**承载信息**的文字一律使用 `secondary` 及以上；`muted` 只用于装饰性 mono kicker（`rail-caption`、`section-kicker` 一类），且其内容必须在别处以合格对比度重述一遍。
3. **动效**：步骤点的 `transition: all .3s` 与 loading 旋转属非信息性动效；信息变化同时以文字呈现，满足 `prefers-reduced-motion` 降级。
4. **键盘与语义**：`el-select` 沿用 Element Plus 原生键盘操作（↑↓ / Enter / Esc）；区块标题与控件建立 `aria-labelledby` 关联；日志流容器 `role="log"` + `aria-live="polite"`，**但不得逐行播报**（2s 轮询节奏下会造成刷屏）；阶段带与 ERROR 行为状态变化点，其文字本身即播报内容。
5. **不依赖记忆**：致命性、既存键来源、恢复路径都以文字写在界面内，不要求用户记住上文（§6.1 的用词理由）。

**响应式**

| 断点 | 行为 |
| --- | --- |
| ≥ 1440（1920 主档） | 现状布局：`232px` rail + 内容区；步骤 2 为 `10 / 14` 分栏 |
| ≤ 1366 | 内容区收窄，`el-select` 保持 300px；步骤 2 分栏不换行 |
| ≤ 900（`deploy.vue:2685`） | rail 收窄至 190px，`stage-header` / `step-content` 横向内边距降为 18px；步骤 2 分栏换为单列 |
| ≤ 680（`deploy.vue:2699`） | rail 移到顶部、`stage-index` 缩到 22px；控件宽度 100% |
| 日志对话框 | 固定 700px 宽，视口 < 740px 时按既有实现收缩；日志行 `word-break: break-word`（既有）保证长文案换行不溢出 |

2. **`imageTag` 落位失败时的界面后果**（§14.2 行 4 / RISK-12 / AC-14）。若某目录条目只声明 `imageTag`、无 `patches` / `scripts`，而 tag 又落不进 compose 生成，向导会让用户选一个「看上去可选、实际什么都不做」的版本——正是 PRD 禁止的假资料效果，只是成因不同。请判定：该情形下是否**不展示该条目**，或展示时必须标注不生效。本文的「步骤预览」在 `patches` 与 `scripts` 皆空时会显示「该版本无部署扩展步骤」，但**不足以挡住该误选**，需设计层结论。
3. **阶段带与「扩展」步骤点的触发源**（§14.2 行 6 / BR-10）。本文 D-03 以「是否真的进入扩展阶段」为触发（P3），不依赖百分比区间；请确认由 `status` / `statusText` / `stage` 中的哪一个驱动（现状：`stage` 被前端完全丢弃，`progress-steps` 是纯百分比分桶）。**本设计不要求分配百分比**，数值以你的区间结论为准（原型内已标「示意」）。
