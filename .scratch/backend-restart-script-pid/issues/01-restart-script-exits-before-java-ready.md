# 01: 后端重启脚本把 cmd.exe 启动器 PID 当成 Java PID，误报启动失败

Status: resolved
Type: bug
来源: 2026-10-20 本地后端重启与真实部署验证

## 现象

执行 `backend/scripts/rebuild-restart.ps1` 后，脚本有时在 Java 已经启动并监听
`8080` 之前报告：

```text
[ERROR] 进程已退出，启动失败
```

但随后 `http://localhost:8080` 实际可以正常访问，说明后端启动成功，脚本的
进程存活判断与真实 Java 进程不一致。

## 复现路径

1. 在 Windows 上停止现有后端；
2. 执行 `backend/scripts/rebuild-restart.ps1 -SkipCompile -SkipPlugins`；
3. 脚本通过 `Start-Process` 启动临时 `start-backend.bat`；
4. `cmd.exe` 包装器很快退出，Java 继续在后台启动；
5. 脚本检查包装器 PID 时发现进程不存在，立即报启动失败；
6. 稍后检查 `8080` 端口，Java 已正常监听并通过登录健康检查。

## 根因

`Start-Process` 返回的是 `cmd.exe` 启动器 PID。当前脚本把该 PID 同时写入
`backend/logs/game-platform-manager.pid`，并在等待循环中用
`Get-Process -Id $processId` 判断 Java 是否存活。`cmd.exe` 退出不代表
Java 退出，因此启动过程被提前判失败。

## 期望

- 启动就绪判断以目标端口监听和应用健康检查为准，不以 `cmd.exe` 包装器
  的存活状态为准。
- `game-platform-manager.pid` 记录实际监听 `8080` 的 Java 进程 PID，或明确
  改名为启动器 PID 并另外记录 Java PID。
- 包装器已退出但 Java 仍在启动时，脚本继续等待到超时；只有 Java 未监听、
  健康检查失败且没有可确认的 Java 进程时才报告失败。
- 停止脚本仍能通过 PID 文件安全停止后端，不误杀 PID 复用后的其他进程。
- 成功启动和真实失败都能返回正确退出码，便于上层
  `scripts/rebuild-restart-all.ps1` 判断结果。

## 验收

- [x] 回归测试或可重复脚本验证覆盖“`cmd.exe` 很快退出、Java 随后监听”场景。
- [x] 启动成功后 PID 文件中的 PID 与 `8080` 监听进程一致。
- [x] Java 真的启动失败时脚本返回非零退出码，并输出应用日志尾部。
- [x] 正常重启后登录健康检查通过，上层全栈脚本不再误报。
- [x] 停止流程使用实际 Java PID 仍能正常停止本次启动的后端。

## Out of scope

- 用全局进程名或端口范围批量杀进程。
