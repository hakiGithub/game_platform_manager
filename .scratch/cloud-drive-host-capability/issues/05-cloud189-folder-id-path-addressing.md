# 05: 天翼账号的目录浏览/起始目录输入混用了 ID 与路径语义

Status: ready-for-human
Type: bug
来源: CloudDriveService 真实天翼账号验证（2026-10-20）

## 现象

`GET /api/cloud/accounts/live-189/folders?path=/` 和 `path=/maps` 可正常列出目录，
但以接口返回的 ID 型 `value` 作为下一次 `path` 查询参数时会返回
`folder not found`。

天翼 SDK 返回的 `CloudObject` 同时包含业务路径 `path` 和目录 ID。当前接口
为 ID 型 provider 返回 `value=id`，而 `listFolders` 和
`listAccountFolders(sdkAccountId, path)` 接收的是路径；前端目录级联使用
`node.data.path` 可绕过该问题，但公共 API 的 `value` 契约仍然自相矛盾。

起始目录进一步暴露了边界问题：ID 型 provider 的 `value` 被直接交给
`createMount(..., rootPath)`，而 SDK 的 mount 层把 `rootPath` 归一化为路径
（`DirectoryRef`），没有公开的“文件夹 ID → 根路径”解析入口。选择根目录
`-11` 或子目录 ID 时，后续路径可能变成 `/-11/...` 并被 SDK 按名称逐段解析，
导致 `folder not found`。

## 复现路径

1. 使用有效天翼账号调用 `GET /api/cloud/accounts/{name}/folders?path=/`。
2. 取得 `path` 与 `id` 不同的子目录项。
3. 把该项的 `id`（当前 ID 型 provider 的 `value`）作为下一次 `path` 查询参数。
4. 接口返回 `folder not found`；把该值用于起始目录时也缺少稳定的 ID→路径映射。

## 期望

- 前端回填的 `value` 必须能被明确声明的消费方正确使用。
- 目录浏览接口只接受路径；每次响应同时保留 `id`、`path`，并明确 `value` 的用途。
- ID 型 provider 的起始目录必须有经过验证的 ID→根路径/挂载映射，不能把 ID 直接当 path。
- 根目录、一级子目录和更深层级均可连续浏览，并可用于起始目录。

## 验收

- [ ] 有效天翼账号从 `/` 依次进入 `/maps`、`/maps/<子目录>` 等层级成功。
- [ ] 响应中的 `path` 可用于下一次 `GET .../folders`，并返回该目录的子项。
- [ ] ID 与路径不同时不会把 ID 当作路径传给 `listAccountFolders`。
- [ ] 以 `-11` 或子目录 ID 作为起始目录后，挂载根可正常 list/download。
- [ ] 增加服务层或 SDK 契约回归测试，覆盖路径型/ID 型 provider 的浏览与起始目录语义。
- [ ] 其他 provider 的目录浏览和起始目录行为不回归。

### 2026-10-20 Triage 结论

**分类：** bug
**状态：** ready-for-human

源码与相邻 SDK 契约已核对：

- `CloudObject.path` 是账号内绝对路径，`listAccountFolders(accountId, path)` 只接受路径。
- 当前 `listFolders` 同时返回 `id`、`path`，但 ID 型 provider 的 `value=id` 容易被误当作下一次
  `path` 查询参数；前端级联目前使用 `node.data.path`，因此页面主流程未必触发，公共 API 契约仍冲突。
- `applyRootDir` 把 ID 型 `value` 直接传给 `createMount(..., rootPath)`；SDK 的 mount 层用
  `DirectoryRef` 归一化为路径，没有公开的文件夹 ID 到根路径解析入口。因此 ID 型起始目录
  的完整语义无法只靠平台侧拼字符串安全实现。

本票需要先决定跨 SDK 边界的契约：目录浏览只接受路径；ID 型起始目录要么由 SDK 提供
“文件夹 ID → 账号内路径”的解析能力，要么由平台在应用起始目录时把 ID 转换为已校验的路径。
未经真实路径解析的字符串拼接会再次产生 `/-11/...` 形式的错误寻址，因此不在本票里临时修补。
