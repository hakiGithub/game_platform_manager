# 05: UTF-8 插件配置描述按 GBK 读取后乱码

Status: resolved
Type: bug
来源: 2026-10-20 问题 03 真实验证

## 现象

在实例 97 的 L4D2 插件配置接口中，`自选-多特感插件` 的
`specialspawner.cfg` 配置项已经能解析出描述，但 UTF-8 中文描述返回为乱码，
例如 `ss_base_limit` 的 description 无法阅读。

同一文件 `rawContent` 中的中文注释也显示为乱码，而接口 JSON 使用 UTF-8，
说明乱码发生在后端读取 cfg 字节时，不是前端显示或终端编码问题。

## 根因

`SourceModCfgService` 固定使用 `GbkCodecUtil.gbk()` 调用
`InstanceFileService.readTextFile(...)`。当前 cfg 实际为 UTF-8 无 BOM，
中文被按 GBK 解码后产生乱码。

同时 `InstanceFileServiceImpl.writeTextFile(..., Charset)` 没有把 charset
参数传到 Native/Docker 写入链路，部分写回路径仍使用默认或 UTF-8 编码。

## 期望

- SourceMod cfg 读取时自动识别 UTF-8（含无 BOM）与 GBK。
- 写回时沿用读取时识别出的编码，避免保存后中文再次损坏。
- Native 与 Docker 两条文件写入链路都尊重显式 charset。
- 回归测试覆盖 UTF-8 无 BOM 中文描述、GBK 中文描述和显式编码写回。

## 验收

- [ ] UTF-8 无 BOM 的 cfg 中文描述不再乱码。
- [ ] GBK cfg 保持原有读取和写入行为。
- [ ] 插件配置读写在 Native/Docker 路由下都使用识别出的编码。
- [ ] 相关单元测试与真实实例配置复核通过。

### 2026-10-20 实施与真实验证

**根因**

`SourceModCfgService` 固定按 GBK 读取 cfg。实例 97 的
`specialspawner.cfg` 实际是无 BOM UTF-8，中文描述因此被错误解码。

`InstanceFileServiceImpl.writeTextFile(..., Charset)` 此前也没有把 charset
传到 Native / Docker 写入链路，存在保存后再次损坏的风险。

**实现**

- `GbkCodecUtil.decodeAutoWithCharset()` 增加严格 UTF-8 判定：UTF-8 BOM
  或无 BOM 严格解码成功使用 UTF-8，否则回退 GBK，并返回实际 charset。
- `SourceModCfgService` 读取 cfg 时先取原始字节自动判码，写回和恢复默认值
  时沿用读取 charset。
- `FileAccessService` / `FileService` / `InstanceFileServiceImpl` 的写入链路
  完整透传 charset，Native SFTP 与 Docker 临时文件均按指定编码写入。
- 回归测试覆盖 UTF-8 无 BOM 中文描述、GBK 回退、Native 与 Docker 编码透传，
  以及配置页面中文可读性断言。

**真实验证**

- `GbkCodecUtilTest`、`SourceModCfgServiceTest` 通过。
- `InstanceFileServiceImplTest` 通过。
- 全栈重启后实例 97 `specialspawner.cfg` 的 `ss_base_limit` 描述返回
  `生还者团队不超过4人时有多少个特感`，不再包含乱码字符。
- Playwright `plugin-config-multifile-live.spec.js` 1/1 通过，页面描述列
  中文可读且不泄漏 `Minimum:` / `Maximum:`。
