# 07: VPK 分析脚本在 --volumes-from 下用工具容器根目录读目标文件

Status: resolved
Type: bug
来源: Issue 06 工具镜像修复后的真实接口验证（L4D2 实例 97，2026-10-20）

## 现象

`platform-tools` 镜像补齐 Python 后，实例 97 的 mission 请求不再报
`exec: "/usr/bin/python3": executable file not found`，但仍返回：

```json
{
  "code": 400,
  "message": "解析 mission 失败: 文件不是有效的 L4D2 地图 VPK（无 mission 信息）: red_square.vpk",
  "data": null
}
```

目标 VPK 实际有效：版本 1、目录树 84176 字节，其中存在
`missions/redsquare.txt`，数据区偏移 378050552、大小 6322。

## 根因

`backend/core/src/main/resources/tooling/vpk_analyze.py` 的
`read_data_section` 原先把 VPK 路径直接传给 Python `open()`：

```python
with open(path, "rb") as f:
```

但当脚本通过 `--volumes-from <目标容器>` 在临时工具容器内执行时，
`path=/l4d2/left4dead2/addons/red_square.vpk` 只存在于目标容器卷的根
命名空间，不在工具容器自己的 `/` 下。工具容器又同时挂载了 `/s` 脚本目录，
因此 `open()` 打开的是工具容器根文件系统中的同名路径（不存在或不是目标
文件），导致 `read_data_section` 返回空列表。

目录树本身能正常读取，因为主流程先 `open(path, "rb")` 读 header/tree；
真实接口失败点发生在 mission 数据区补读阶段。单独在目标卷命名空间中执行
同一份脚本可以正确解析出 `Red Square Campaign` 和 5 个章节。

1. 保持 L4D2 实例 97 运行，目标容器内
   `/l4d2/left4dead2/addons/red_square.vpk` 可读。

   `registry.cn-shenzhen.aliyuncs.com/haki_hub/platform-tools:latest` 内有
   `/usr/bin/python3`。
3. 执行：

```powershell
$login = Invoke-RestMethod -Uri 'http://localhost:8080/api/auth/login' `
  -Method Post -ContentType 'application/json' `

Invoke-RestMethod -Uri 'http://localhost:8080/api/plugin/l4d2/maps/red_square.vpk/mission?instanceId=97' `
  -Headers $headers
```

实际返回 `无 mission 信息`，而非标题和章节。

### 2026-10-20 实施与真实验证

**根因与实现**

- 原实现用 `--volumes-from <目标容器>` 复用卷命名空间，但同时把脚本目录挂到
  `/s`；工具容器中的绝对路径与目标容器根目录不是同一个文件系统视图。
- 工具容器现在通过 `docker inspect` 读取目标容器挂载，选择覆盖 VPK 路径的
  最长 mount destination。
- 命名卷使用 volume name，bind mount 使用宿主 source；统一只读挂载到
  `/gp-target/<原 destination>`，根 destination 映射到 `/gp-target`，避免覆盖
  工具镜像自己的 `/usr/bin/python3`。
- 脚本读取 `GP_VPK_TARGET_ROOT`，将目标容器内的绝对 VPK 路径映射到工具容器
  的独立挂载根；header、目录树和数据区使用同一路径语义。
- 支持 `archiveIndex=0x7FFF` 与 `0xFFFF` 两种“数据在当前 VPK 文件”的哨兵值。
- 拒绝危险根路径、悬空挂载和过宽 bind mount source。
