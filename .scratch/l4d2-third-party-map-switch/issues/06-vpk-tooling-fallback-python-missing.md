# 06: VPK 工具容器 fallback 使用 Python 入口但镜像/目标容器不可用

Status: ready-for-human
Type: bug
来源: Issue 05 修复后的真实接口验证（L4D2 实例 97，2026-10-20）

## 现象

主应用 SDK 对齐后，请求：

```http
GET /api/plugin/l4d2/maps/red_square.vpk/mission?instanceId=97
```

返回可读业务错误：

```json
{
  "code": 400,
  "message": "解析 mission 失败: VPK 分析失败: docker: Error response from daemon: failed to create task for container: ... exec: \"python3\": executable file not found in $PATH",
  "data": null
}
```

同一时刻地图列表能通过识别缓存正常返回 `Red Square Campaign` 和 5 个章节，
但详情接口无法在目标容器或工具容器中执行 VPK 分析脚本。

## 根因

`VpkToolingAnalyzer` 的 Docker 路径在目标容器没有 `python3` 时，会启动
`platform-tools` 临时容器并以：

```text
--entrypoint python3
```

执行分析。当前使用的 `platform-tools` 镜像没有可在该路径找到的 `python3`
可执行文件，导致 Docker 在容器 init 阶段失败。错误因此不是 VPK 损坏、
文件名错配或地图内容缺失，而是工具容器运行时依赖不满足。

## 期望

- 目标容器缺少 `python3` 时，平台工具容器能可靠执行 VPK 分析，或明确返回
  “工具镜像缺少分析运行时”并按可操作方式提示。
- `platform-tools` 的镜像契约与 `VpkToolingAnalyzer` 实际使用的入口保持一致：
  镜像内必须有固定的 Python 解释器路径，或者分析脚本改用镜像已有的运行时。
- 工具容器启动失败时不暴露 Docker 守护进程的长内部回显；响应保留目标
  VPK 名、失败阶段和可操作建议，日志保留脱敏后的底层错误。
- 工具镜像不可用、目标容器不可用、VPK 文件不可读三类失败能区分。

## 验收

- [ ] 在目标 L4D2 容器没有 `python3` 的真实环境中，mission 详情能成功读取
  `red_square.vpk` 的标题和章节，或者给出不会误导为 VPK 损坏的工具运行时错误。
- [ ] `platform-tools` 镜像的 Python 入口与代码引用一致；镜像构建/发布检查
  覆盖该入口。
- [ ] 临时工具容器失败时，错误响应包含 VPK 名、失败阶段和恢复建议，不泄露
  密码、SSH 凭据或环境文件内容。
- [ ] 增加 Docker 路径回归测试，覆盖目标容器无 `python3`、工具容器入口存在、
  工具容器拉取失败和临时脚本清理。
- [ ] 真实实例 97 复测并记录使用的镜像 digest 与解释器路径。

## Out of scope

- 修改 `red_square.vpk` 的内容、裁剪或重新上传。
- 修复游戏运行时看不到地图的问题；该问题仍由 Issue 02 跟踪。
- 在插件中自行调用裸 Docker 命令，绕过 `HostToolingService`。

拉取并复测 mission 接口。发布完成前，Issue 07 的实现可以保留，但存量主机
仍应按部署说明重新拉取工具镜像。
