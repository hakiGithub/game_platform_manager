# 01: Docker Compose 卸载未检查工作目录清理结果

Status: resolved
Type: bug
来源: Issue 05 真实部署验证（2026-10-19）

## 现象

真实部署 dnf-tw Docker Compose 实例后，通过平台删除实例时，`DockerComposeAdapter.uninstall` 会执行：

```text
rm -rf <workDir>
```

该命令以 SSH 普通用户执行，但 dnf-tw 的 MySQL bind mount 可能生成 root 所属文件。命令失败时当前实现没有检查返回结果，仍继续上报卸载成功，导致：

- 实例记录和容器可能已删除；
- 远端工作目录及 root 所属数据仍残留在主机上；
- 用户无法从删除操作结果得知清理未完成。

## 复现路径

1. 使用普通 SSH 用户在目标主机部署 dnf-tw Docker Compose 实例；
2. 等待 MySQL 初始化并产生 root 所属的 bind mount 文件；
3. 通过平台删除实例；
4. 检查远端实例工作目录是否仍存在。

## 期望

- 删除工作目录必须检查 SSH 命令的 exit code 和错误输出。
- 清理失败时不能静默上报完全成功；应返回明确失败结果，或在平台能力范围内完成安全提权清理。
- 不得通过无界提权或对未知路径执行删除来掩盖失败。
- 明确普通 SSH 用户无法删除 root 所属文件时的产品行为：提示残留路径、保留可重试状态，或采用经过确认的提权策略。

## 验收

- [ ] 工作目录删除失败时，`uninstall` 不返回完全成功且记录明确错误。
- [ ] 普通 SSH 用户 + root 所属 bind mount 的回归测试覆盖失败路径。
- [ ] 成功清理路径仍能删除工作目录并保持现有删除流程可用。
- [ ] 删除命令对路径做明确边界校验，避免 `rm -rf` 误删非实例目录。
- [ ] 真实环境复现后确认没有再出现“API 删除成功但目录残留且无提示”的情况。

## Out of scope

- 修改 dnf-tw 的 compose 模板或 MySQL 数据目录布局。
- 无条件使用 root 或引入新的远程提权机制。
- 其他与卸载清理无关的实例删除行为。

### 2026-10-20 Triage 结论

**分类：** bug
**状态：** ready-for-agent

已在真实 dnf-tw Docker Compose 部署清理中确认：普通 SSH 用户执行 `rm -rf <workDir>` 时，MySQL bind mount 产生的 root 所属文件会让清理失败，但当前 `DockerComposeAdapter.uninstall()` 不检查 `SshUtil.CommandResult`，随后仍返回成功。

实例删除链路还有一条必须保留的既有约定：远程卸载失败或抛异常时，只记录警告，继续物理删除数据库记录，避免残留记录阻止用户重新部署。因此仅让 `uninstall()` 返回 `false` 仍会被 `InstanceServiceImpl.deleteInstance()` 吞掉，不能解决“用户完全不知道目录残留”的问题。

现有平台没有已确认的通用 sudo/提权契约；本票不引入新的提权机制。产品行为应是保留删除记录的能力，同时把部分成功与残留路径明确回传给调用方并记录到可观察日志。

`LinuxGsmDockerAdapter.uninstall()` 和更新/清理路径也存在未检查的 `rm -rf`；本票要求将安全的工作目录删除收敛到共享能力，至少覆盖 Docker Compose 与 LinuxGSM Docker 的卸载路径。`DockerAdapter.uninstall()` 本身通过 Docker API 删除容器，不属于 shell 工作目录清理；除非验证发现同类问题，否则不扩大修改范围。

## Agent Brief

**Category:** bug
**Summary:** 远程卸载清理失败时必须保留实例删除语义，同时返回并记录明确的部分成功与残留目录

**Current behavior:**

Docker Compose 与 LinuxGSM Docker 卸载通过 SSH 执行未加引号的 `rm -rf <workDir>`，不检查退出码和错误输出。dnf-tw 的 MySQL bind mount 文件属于 root 时，普通用户清理失败，但适配器仍返回成功。上层删除服务即使收到 `false` 也只记录一条警告并继续删除数据库记录，因此前端最终看到删除成功，用户不知道远端目录仍残留。

**Desired behavior:**

工作目录清理必须是可验证的操作：路径先做安全校验并正确引用，再执行删除；执行后检查退出状态。路径为空、根目录、家目录、仅由 `/` 或多个点构成的危险值必须拒绝，不能对未经确认的路径执行递归删除。

清理成功时卸载结果与现有行为一致。清理失败时不得报告完整成功；结果需要区分“容器/服务已处理”和“工作目录仍残留”，包含经过脱敏的残留路径与可读错误。实例删除仍按既有约定继续物理删除数据库记录，但 API 响应必须能让用户看到部分成功；如果当前调用契约无法携带部分成功信息，就扩展删除结果 VO，而不是把失败吞成空成功。

适配器日志应保留失败命令、退出码、错误输出和残留路径；日志不得输出密码、数据库凭据或完整环境文件内容。不得为了清理成功而无条件使用 root、`sudo`、`su` 或远程提权命令。

**Key interfaces:**

- `DeployAdapter.uninstall()`：当前只返回 `boolean`；至少应表达成功、失败和部分成功，或提供可查询的失败原因。
- `DockerComposeAdapter.uninstall()` 与 `LinuxGsmDockerAdapter.uninstall()`：`rm -rf` 调用必须检查 `SshUtil.CommandResult`、路径边界和 shell 引号。
- `InstanceServiceImpl.deleteInstance()`：当前忽略 `false` 仍删库；保留记录删除语义，同时把清理结果传给控制器/VO。
- 实例删除控制器与前端删除流程：成功删除记录但远程清理失败时，显示明确的警告与残留路径，不得显示纯成功。
- 共享工作目录安全清理能力：若适用，复用同一路径校验和结果模型，避免两个适配器各自实现。

**Acceptance criteria:**

- [ ] 路径含空格、引号或 shell 元字符时，删除命令仍只作用于校验后的目标目录。
- [ ] 空路径、`/`、家目录和越界路径被拒绝，且不执行递归删除。
- [ ] `rm -rf` 返回非零时适配器不报告完整成功，并记录退出码、错误输出和残留路径。
- [ ] 容器已停止/删除但工作目录清理失败时，数据库记录仍按现有约定物理删除。
- [ ] 删除接口向调用方返回部分成功状态和可定位的残留信息；前端显示警告而不是纯成功。
- [ ] 成功清理路径保持现有卸载行为，不产生额外阻塞或误报。
- [ ] 测试覆盖成功、非零退出、root 所属文件模拟、危险路径、含空格路径和上层部分成功传播。

**Out of scope:**

- 修改 dnf-tw 的 compose 模板、MySQL 数据目录布局或容器运行用户。
- 引入新的 sudo、root 或远程提权机制。
- 自动删除清理失败后仍残留的 root 所属文件。
- 重构与实例卸载无关的文件管理删除逻辑。

### 2026-10-20 实施与真实验证

**实现**

- 在 `AbstractDeployAdapter` 收敛工作目录边界校验、POSIX 路径规范化、
  shell 单引号引用、非零退出码检查和残留路径返回。
- `DockerComposeAdapter` 与 `LinuxGsmDockerAdapter` 的卸载及更新清理路径
  统一使用该能力，不再对未校验路径直接执行 `rm -rf`。
- `UninstallResult` 区分 `success`、`partial_success`、`failed`；
  `InstanceDeleteResultVO` 返回 `deleted`、`remoteCleanupStatus`、`message`
  和 `residualPaths`。
- 实例删除仍遵循既有约定：远端清理失败不阻止数据库记录物理删除，
  但 API 和前端必须明确展示部分成功与残留路径。

**真实隔离验证**

1. 成功路径：工作目录内存在 `root:root 600` 文件，但父目录可遍历。
   删除接口返回 `remoteCleanupStatus=success`，容器、网络、工作目录和数据库

   同时确认 compose 容器和网络已删除、数据库记录已物理删除、残留目录仍
   存在。随后仅用预先校验的一次性绝对路径和 root 临时容器清理该目录；
   未执行全局 prune，未触碰实例 97、99。

验证结论：卸载失败不再被静默吞成完整成功，记录删除语义保留，API 与前端
