# 03 — 任务状态词汇表被两个前端重新实现，插件侧还有两个枚举外的状态

**Status:** needs-triage
**Type:** task
**来源:** 架构评审 2026-10-21（候选 3，强度 Worth exploring）

## 现象

后端 `backend/core/.../enums/TaskStatus.java` 已是任务状态机唯一 owner，
自带 `isTerminal()` 与 `canTransitionTo()`。但两个前端各自重新声明这套词汇：

| 侧 | 文件数 | 字面量数 |
|---|---|---|
| 主应用 `frontend/src` | 15 | 42 |
| 插件 `backend/plugin-l4d2/frontend/src` | 14 | 78 |

合计 **120 处** `PENDING / RUNNING / COMPLETED / FAILED / CANCELLED` 字面量，
分布在任务详情、部署进度、备份进度、还原确认、地图下载、插件安装等场景。

（初版 HTML 报告写「125 处」，实测为 120，以本表为准。）

**枚举外状态**：插件侧 `api/index.ts:483` 定义了

```
STORE_TASK_RUNNING_STATUSES = ['PENDING', 'RUNNING', 'DOWNLOADING', 'INSTALLING']
```

`DOWNLOADING` 与 `INSTALLING` **不在 `TaskStatus` 枚举中**。这两个词是插件 UI 自己造的
「进行中」状态，用来让任务条保持转圈。后端状态机不认识它们，所以：

- 若后端某天返回这两个词，主应用侧的状态映射会落到兜底分支。
- 插件侧判断「任务是否还在跑」靠这张自建表，与 `TaskStatus.isTerminal()` 是两套真值源。

## 根因

SDK 的 `TaskVO` 只暴露 `status` 字符串，没有把**状态机**本身递过去。
于是每个调用方自己判断「是否终态」「是否在跑」。上一轮评审（票 06）已把
轮询节奏与进度窗口收口到 `ChildTaskFollower`，但**状态词汇的解释权**仍在各调用方手里。

## 修复建议

让后端在任务 VO 上直接给出语义，前端只留展示：

- 任务 VO 增加 `terminal: boolean`（或 `progressPhase` 枚举），由 `TaskStatus.isTerminal()` 派生。
- 插件侧删除 `STORE_TASK_RUNNING_STATUSES` 的自建集合，改用 VO 的终态判断；
  `DOWNLOADING` / `INSTALLING` 降级为**进度阶段**（progress message），不再是状态。

## 验收

1. `TaskStatus` 仍是状态机唯一 owner；`isTerminal()` 的判断只存在于后端。
2. 插件侧不再有枚举外的状态词；`DOWNLOADING` / `INSTALLING` 变为进度阶段或文案。
3. 主应用侧 42 处字面量中，判断「是否终态」的部分改为消费 VO 字段；
   纯展示的标签映射可保留（与 ADR-0005 的 UI 元数据例外一致）。
4. 有单测覆盖：新增状态词时前端不会静默落到兜底分支（或明确断言兜底行为）。

## 关联

- **ADR-0007**（插件前端复制而非共享）：若采纳「VO 带终态字段」方案，两个前端都消费
  同一个后端字段，不再需要复制状态词，反而更符合 ADR-0007 的隔离意图。若坚持前端复制，
  则本票退化为修 `STORE_TASK_RUNNING_STATUSES` 的越界状态，工作量小得多。
- 与票 02 同族（词汇表无 owner），但本票涉及跨前后端契约，需先确认 VO 字段是否可加。

### 2026-10-21 评审结论

实测字面量数由初版 125 修正为 120。插件侧两个枚举外状态是本票最具体的痛点：
它让「任务是否还在跑」出现两套真值源。是否推进取决于能否改任务 VO——若不能，
建议降级为修正插件侧越界状态词。
