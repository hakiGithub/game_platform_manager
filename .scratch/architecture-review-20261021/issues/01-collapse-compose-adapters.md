# 01 — 两个 Compose 适配器逐字重复，副本已漂移

**Status:** needs-triage
**Type:** task
**来源:** 架构评审 2026-10-21（候选 1，强度 Strong）

## 现象

`DockerComposeAdapter`（1377 行）与 `LinuxGsmDockerAdapter`（1331 行）各自实现同一批
Compose 部署规则。逐方法比对行级重合度：

| 方法 | 行重合度 | 是否已漂移 |
|---|---|---|
| `getProjectName` | 91% | 否 |
| `generateEnvFileContent` | 85% | 是（46 vs 39 行） |
| `getComposeCommand` | 85% | 是（含日志文案差异） |
| `injectHostCertsMount` | 84% | 是（67 vs 73 行） |
| `ensureVolumesDeclaration` | 74% | 是（60 vs 72 行） |
| `resolveWorkDir` | 73% | 是（28 vs 30 行） |
| `getWorkDir` | 60% | 是（20 vs 14 行） |
| `uploadEnvFile` | 50% | 是 |
| `stripAnsiCodes` | 43% | 是（7 vs 14 行） |
| `summarizeSshError` | 逐字相同 | 否 |

只有 `summarizeSshError` 是逐字相同；其余九项都已各自演化。涉及的行为都是**承重**的：
`mountHostCerts`（AGENTS.md 明文约定 Docker 类部署统一支持、默认关闭）、
env 文件生成、volumes 声明补全、project/workdir 解析、Compose 命令探测与回退。

后果：修其中一份，另一份静默不生效。例如 `mountHostCerts` 相关改动只落在
`DockerComposeAdapter` 上时，`linuxgsm-docker` 部署的证书挂载行为与
`docker-compose` 不再一致，且没有任何测试会红。

## 根因

两个部署方式共享「Compose 编排」这一整块实现，但**没有一个 module 拥有它**。
`DeployAdapter` 接口按部署方式切分，实现却按「是否用 compose」切分，两个维度错位。
`AbstractDeployAdapter`（794 行、0 个 public 方法）只提供 protected 助手，
没有承担这块公共实现——删掉它复杂度不会回来，但删掉它也不解决问题。

## 修复建议

抽一个深 module 拥有 Compose 编排：项目/workdir 解析、compose 文件合成、env 文件、
volumes 声明、host certs 挂载、端口映射、生命周期、ANSI 剥离。
`DeployAdapter` 保持为接口；两个适配器退化为「风味」——只提供自己的 compose 模板
与启动步骤（`linuxgsm-docker` 的 `docker exec` 就绪探测、`details` 校验）。

```
ComposeDeployModule
  interface: deploy / start / stop / restart / status / details / logs /
             update / uninstall
  impl:      上述公共实现，DeployFlavour 选择模板与启动步骤
```

## 验收

1. `mountHostCerts` 与 env 文件规则各只有一处实现。
2. 两个部署方式的 `validateEnvironment` / `uninstallWithResult` / `getDetails` 行为不变，
   现有 `DockerComposeAdapterTest` 全绿，并为 `LinuxGsmDockerAdapter` 补对应用例集。
3. 两个适配器合计净减 ≥ 400 行。
4. 一条回归测试证明两个风味走同一份 certs/env 逻辑（同一 config，两条部署路径）。

## 关联

- 与票 04（部署配置类型化）天然衔接：类型化后的 `DeployConfig` 正是这个 module 的入参。
- 与 ADR-0008 无冲突：插件只提供配置，执行仍走适配器体系。
