# 05 — 实例文件访问靠 20 处 isNative 分支区分两种传输

**Status:** needs-triage
**Type:** task
**来源:** 架构评审 2026-10-21（候选 5，强度 Speculative）

## 现象

`InstanceFileServiceImpl`（688 行）同时服务两种传输：宿主机 SSH 与容器内
`docker exec` / `docker cp`。区分方式是 `route.isNative()`，全文件 **20 处分支**，
外加 24 处 `docker exec` / `docker cp` 引用。

典型形态（上传路径）：

```
native:  SFTP 上传到 installPath
docker:  SFTP 上传到宿主机临时路径 -> mkdir -p（容器内）-> docker cp 进容器
         -> 删除宿主机临时文件
```

后半段（临时文件生命周期、失败清理）**只属于 docker 路径**，却写在同一个方法体里，
与 native 路径共享 try/catch 尾段。native 路径永远看不到这些代码，却要承担它的复杂度。

`srcRoute.isNative() != dstRoute.isNative()` 的组合判断出现 4 次（跨路由操作）。

## 根因

`AbstractInstanceFileService` 已有正确的 seam 设计：`buildRoute` 由子类实现，
`FileRoute` 承载路由上下文。但**路由之后的行为没有跟着分叉**——
只有路由分叉了，执行没有。于是传输差异以 `if` 的形式留在每个方法里。

## 修复建议

沿已有 seam 把实现拆成两个 adapter：

```
InstanceFileAccess (已有接口)
  ├── NativeFileAccess     : 直接 SFTP + 宿主机命令
  └── DockerFileAccess     : 宿主机临时文件 + docker exec/cp + 清理
```

- `FileRoute` 决定选哪个 adapter，只决定一次。
- 临时文件生命周期规则收进 `DockerFileAccess`。
- 跨路由操作（`srcRoute.isNative() != dstRoute.isNative()`）显式建模为
  「宿主机中转」，而不是 4 处布尔比较。

## 验收

1. 传输分支从 20 处降为 1 处（路由选择）。
2. 临时文件创建/清理只在一处实现，失败路径有测试覆盖。
3. 现有 `InstanceFileServiceImplTest` 全绿，行为不变。
4. 跨路由操作的宿主机中转语义显式可测。
